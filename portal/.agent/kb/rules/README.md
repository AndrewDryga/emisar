## House conventions

- **Consistency and reuse beat a one-off — always, unless explicitly asked or genuinely required.** Before adding UI, find the shared component that already renders that shape and reuse it; before styling, copy an existing instance's classes rather than inventing new ones. A one-off is justified only when the user asks for it or no existing component can do the job — and then say why in one sentence. The tell you got this wrong: your element has a background, border, spacing, or icon that matches nothing else on the page (a console `code_line` dropped onto a docs page where every other value is a `docs_code`; a hand-rolled label/value box beside components that already exist). When a surface has a native family — docs pages use `docs_code`/`docs_callout`/`docs_screenshot`, the console uses `code_line`/`stat`/`event_block` — reach for that family's member, not a foreign one that looks almost right. If a shared component is *almost* right, extend it with a narrow prop (a `docs_callout` `icon` override) rather than forking a bespoke copy. Sweep: any bordered/backgrounded value/box/chip on a page whose siblings use a different component for the same job.
- **Icons are semantic assets, never local glyph choices.** `<.icon name="product.runner">` asks `EmisarWeb.Icons` for one MEANING; the drawing lives in exactly one file under `apps/emisar_web/priv/icons/<namespace>/<name>.svg`, and a second `<name>.16.svg` is an optical correction for the 16 px raster, never another icon. One meaning keeps one drawing everywhere, and an overloaded meaning splits by intent rather than growing a near-duplicate to make one screen feel special. Geometry is approved only after literal 16/20/24/48 px raster inspection, monochrome review, independent optical + semantic review, and human signoff. **Colour comes from the call site, and a semantic accent inside a drawing is emphasis, never the whole drawing.** Chrome that LABELS — nav rows, menu rows, tabs — renders monochrome via `emisar-icon-mono`; a solid accent fill carries it too, since the fill already IS the accent — and so does a container TINTED with the icon's own tone family (the flash: rose icon accent on the rose-950 tint had no contrast, so the error mark vanished), where the surface already states the tone. Sweep: an `<.icon>`/`icon=` literal that is not a registry token, an inline `<svg>` or copied path in a template, a local name→glyph map outside the registry, and a component rendering a caller-supplied `icon` inside navigation or a menu panel without `emisar-icon-mono`, plus any deep same-hue tinted container (`bg-<tone>-9xx` at ≥50% opacity) rendering an `<.icon>` whose accents share that tone. **Enforced** by `EmisarWeb.IconsTest` (one owner per meaning, XML-valid masters, content-addressed mask ids, no colour-only anatomy) and `EmisarWeb.TemplateHygieneTest` (every literal name resolves). **A glyph pass is scoped by SURFACE, not by token** — sweeping "every call site of the token I changed" walks past the surface where it sits beside a SIBLING doing the opposite job, because the sibling is a different token (the decisions ledger kept `state.approved`'s box for a day beside an already-plain `state.denied`); look at the rendered SET. Worked rule: `.agent/kb/rules/design-semantic-icon-system.md`.
- **A marker icon names what its section is about**, not a noun it shares with the label. A `state.*`/mode token (`runner.maintenance`, `state.offline`) belongs beside the entity actually in that state; as a heading or disclosure marker it asserts a fact the page never claims and its accent reads as a verdict (the quickstart troubleshooting block wore `runner.maintenance` over a host that never connected). Sweep: every `<.icon>` inside a `<summary>`, heading, or docs/marketing row label, read against the text beside it. Worked rule: `.agent/kb/rules/design-semantic-icon-system.md` §7.
- **Third-party marks inherit the surface's visual system, not a vendor tile** — keep the silhouette and an accessible name, but match sibling first-party icons; no full-colour logo tiles inside dark chrome. `design-console-ux.md` §7.38.
- **Model-facing authoring mutations return domain-owned actionable validation before they write.** Keep the complete versioned contract in discovery so a model can author against it, but do not let a generic transport validator erase array indexes, collapse paths, or truncate the domain's useful issue set. Worked example: `../.agent/kb/rules/elixir-model-authoring-validation-is-actionable.md`.
- **Model edits update the single sha-locked draft in place; publication is human-only; only the live release executes.** A model replaces a runbook's one unpublished change under the same slug, always carrying the definition hash it read, and never mints a version or invents a sibling slug. One execution tool owns both paths: a published run names the LIVE `slug@release` (an older one is `not_live`), and a draft run needs `allow_draft` plus the exact content hash. Worked example: `../.agent/kb/rules/elixir-model-runbook-edits-update-the-draft.md`.
- **UI terminology and code terminology are ONE vocabulary.** What the operator sees is what the code says — schema columns, context functions, filter params, and UI labels share the same noun (the audit trail's acted-upon entity is `target` in the column header AND in `audit_events.target_kind`; it was renamed from `subject`, which also collided with `%Auth.Subject{}`). When a UI label improves, rename the code to match in the same change — never let the interface and the domain model drift into two dialects.
- **An action label names the operator-visible outcome, not an internal intermediate record.** A requester cancels a run; the cancellation may also close its pending approval request, but `Withdraw request` makes the operator guess which object survives. Keep the resource noun and verb stable from trigger through confirmation and result. The same boundary applies to purchase intent: before the payment action, present the selected plan and cadence as facts; reserve `checkout` for a control that actually opens checkout. Sweep: action labels named for an incidental child record, and pre-checkout selection summaries phrased as `Team checkout`.
- **Continuous framed grids keep one track system** — adjacent bordered rows align their dividers; reuse the parent tracks with spans rather than stacking mismatched ones. `design-console-ux.md` §7.39.
- **Scrollable form controls own dark scrollbar chrome** — every shared textarea carries `.scrollbar-control`; the OS default is a bright seam on Windows. `design-console-ux.md` §7.40.
- **A secondary rail never outweighs the primary task.** Delay a fixed-width help, detail, or decision rail until the remaining task column is visibly wider than the rail; stack it below the task at narrower widths. Sweep: fixed `22rem`/`340px` secondary tracks introduced at `lg`, especially inside console layouts that already spend width on navigation, plus `border-l` on reading rails. Worked example: `.agent/kb/rules/design-secondary-rails-never-outweigh-primary-task.md`.
- **A responsive rail may hide help, never an active setting.** Keep interactive controls and read-only current settings in document flow; below the rail split, stack them after the primary table or list and hide only optional explanatory content. Sweep: breakpoint-hidden rail wrappers containing a form, gated setting, or current account value. Worked example: `.agent/kb/rules/design-secondary-rails-never-outweigh-primary-task.md`.
- **Complex editors follow the operator's decision order, not the schema's field order.** Put shared context and run-time inputs before ordered workflow units; when available behavior depends on scope, choose targets first and derive the compatible choices from them. Sweep: editors leading with IDs/version selectors unrelated to the unit overview, behavior selectors that ignore earlier scope choices, related desktop controls split across rows, controls misaligned because their wrappers rather than control boxes share a top edge, equally stretched finite controls, conditional controls that shift earlier fields, delimiter-joined contract metadata, controls shown in modes where they do nothing, status/version facts placed after the identity fields they qualify, duplicate exit navigation or generic headings in action rails, action controls detached from the validation they govern, and side rails ordered before the primary form on mobile. Worked example: `.agent/kb/rules/design-complex-editors-follow-decision-order.md`.
- **A large finite catalog uses the shared searchable selector.** Keep the closed face to the concise identity an operator recognizes; put title, pack, group, and other disambiguating metadata in the searchable panel instead of concatenating it into the control. Sweep: long native selects, catalog labels that join every metadata field into the trigger, and one-off searchable dropdowns that duplicate the Audit Type control. Worked example: `.agent/kb/rules/design-complex-editors-follow-decision-order.md`.
- **Multi-target controls keep one stable overview-row trigger.** Summarize recognizable selected identities in that trigger; a count alone is not a summary, and `+N` is only bounded overflow after named choices. Sweep: overview grids with count-only target triggers, tall multi-line fleet choices, ambiguous `One runner` labels for random selection, server/box/object icons used for target cardinality, redundant `Every online runner`/`Frozen at run start`/`Exact runner` qualifiers, no catalog search, selected scope rows above another picker, raw `group:`/`runner:` refs, stale selections disabled along with add choices, click-owned selected state absent from form serialization, and exact targets nested under a group-selection mode. Worked example: `.agent/kb/rules/design-complex-editors-follow-decision-order.md`.
- **A dependent control never claims an independent failure while its prerequisite is unresolved.** Keep the dependent value visible, neutral, and disabled; let the prerequisite own the actionable error. Sweep: scope-first forms where one unresolved scope produces duplicate rose states or compatibility copy in the behavior control. Worked example: `.agent/kb/rules/design-complex-editors-follow-decision-order.md`.
- **Validation never moves a stable overview row.** When a control already carries the invalid state or unavailable label, attach its explanation and remedy through the shared accessible `<.tooltip>` so validation changes state without changing geometry. Sweep: overview grids whose conditional validation paragraphs change row height. Worked example: `.agent/kb/rules/design-complex-editors-follow-decision-order.md`.
- **A secondary boolean qualifier in an editor is a positive-state checkbox, not a two-option select.** When unchecked means the normal absence and the true state has one clear label (`Required`, `Sensitive`), use the same compact neutral checkbox everywhere with an explicit unchecked form value. Sweep: run-time inputs, outputs, conditions, bindings, and other authoring rows with `Visible/Sensitive`, `Required/Optional`, `No/Yes`, or equivalent false/true selects used only as a qualifier. Worked example: `.agent/kb/rules/design-complex-editors-follow-decision-order.md`.
- **Form cards follow information weight and authoring order, not equal-width filler grids or abstract group names.** Pair fields by the operator's decisions: identity with purpose, behavior choices next, then conditional values, defaults, and bounds. Let field labels carry the hierarchy when that sequence is already clear; do not add a group heading merely to restate it. Cap the collection and give related rows one measure and right edge; within a row, equal binary choices share a compact width while the domain-bearing choice takes the remainder. A monospace identifier does not get a smaller control height. A typed field's editor follows its type: booleans use true/false choices, numerics use numeric controls, and an enum's optional single default is chosen from its allowed values instead of retyped separately. Routine defaults and constraints stay visible; disclosure is for genuinely secondary detail, not a way to reclaim height. Repeated-row actions align to the control surface and peer actions share one enclosure treatment and optical height; repeated-list Add rows receive the collection's normal item gap, and shared components merge caller spacing classes. Button click metadata uses domain-specific `phx-value-*` keys, never `phx-value-value`, which LiveView replaces with the native element value. Sweep: schema-order forms, unnecessary group legends, unconstrained collections, mismatched related-row edges, unequal peer toggles, uniform grids where short selects impersonate primary fields, generic text controls for typed values, enum defaults that can drift outside the allowed set, font changes that alter peer control heights, row actions aligned to a field wrapper rather than its control, mismatched peer action enclosures, generic `phx-value-value` button metadata, normal contract fields hidden behind accordions, replacement headings/dividers left after removing disclosure, orphaned constraint rows, and Add rows touching the preceding card.
- **A form card has one horizontal measure.** Cap the collection or card at the page level; once inside that card, related rows fill its content width and align to the same right edge. Sweep: capped form collections whose cards contain another width cap around their editable rows. Worked example: `.agent/kb/rules/design-complex-editors-follow-decision-order.md`.
- **Ordinary authoring selection stays legible without impersonating a verdict.** Keep its surface, text, and check/radio neutral; the shared choice-card group uses the brand ring to mark the active input on first render as well as after interaction, never a green fill or status treatment. Worked examples: `.agent/kb/rules/design-console-ux.md` §2 and `.agent/kb/rules/design-complex-editors-follow-decision-order.md`.
- **Repeated collections append where the new row appears.** Use the shared full-width dashed `<.add_row>` after the last item; do not put the only Add control in the section header or beside the collection label. Sweep: header/right-aligned `Add …` buttons for inputs, enum values, workflow units, outputs, conditions, overrides, or other repeated configuration. Worked example: `.agent/kb/rules/design-repeated-collections-append-at-end.md`.
- **Approval review leads with human decision evidence, never machine provenance.** Show the action, risk, human runner name, and visible arguments without a disclosure; keep digests, compound runner refs, and database IDs in audit/canonical detail rather than the decision scan. Sweep: approval and confirmation surfaces whose primary rows contain hashes/UUIDs or hide arguments. Worked example: `.agent/kb/rules/design-approval-review-prioritizes-human-evidence.md`.
- **An approval detail states its verdict once and records its provenance once.** Keep the compact status in the page facts; put decider, forensic time, note, and audit receipt in one canonical Decisions ledger at the end of the reviewed record, including a completed 1-of-1 request. Never repeat the same decision as a verdict event block near the header. Sweep: decided approval details that render actor/time/note/audit above the artifact and again in a footer trail, or hide the single-approver trail entirely.
- **A privileged exception stays behind the normal decision until chosen.** Do not give a rare break-glass path a second always-visible form competing with the ordinary action. When the normal action exists, expose the exception from its split-button menu; when policy removes the normal action, keep one compact bordered exception button in the same action cluster. The focused confirmation owns the consequence and required reason; do not add a typed challenge when that reason already supplies deliberate friction. Ask for that reason first, then state the exact exception in the small supporting-copy tier immediately before the actions — never below the commit button. `design-console-ux.md` §5.
- **A live preview repeats the security-relevant effective state it summarizes.** When an editor has a paired “In effect” rail, a warning derived from the edited values appears in that rail as well as beside the controls; share the predicate and warning component so default and scoped editors cannot drift. Sweep: editor-only warnings for state the adjacent preview claims to summarize.
- **An effective-state rail shows its evidence before its warning, in the rail's supporting type tier.** Put the catalog or count breakdown ahead of the warning it qualifies, then render that warning compactly; the same warning beside editable controls may keep the default event-block hierarchy. Sweep: preview-rail alerts that interrupt the summary before its supporting breakdown or visually overpower nearby facts.
- **Moving a warning gives it one new home; it never creates a second copy.** When a warning moves from editable controls into their paired effective-state rail, remove the original and keep one complete instance in the rail. The selected controls already show the configured posture; duplicating the same title and remedy makes the page compete with itself. Sweep: identical warning copy rendered in both a form and its adjacent preview.
- **A conditional section owns its separator.** Put the divider and its padding on the same conditionally rendered wrapper as the content it introduces, so hiding the content removes the line and the space with it. Sweep: always-present borders or empty divider wrappers immediately before conditional warnings, errors, or detail sections.
- **Scope changes revoke stale decisions and contradictory inventory immediately.** Approve and deny both re-read current runner plus pack access at the mutation boundary; an already-open page exits when that access is gone, and Packs rows, contents, and attention counts use the same current pack scope. Hiding a button is never the authorization check. Sweep: approval decisions using socket/session scope, stale detail pages retaining controls after `:not_found`, and account-wide pack projections or badges shown to a pack-restricted member.
- **A mutation is scoped by the same dimension its list is, and it judges that scope on the LOCKED ROW.** When a read narrows rows by a scope dimension (pack access, runner reach), every mutation on those rows narrows by the SAME dimension — a member the list hides a record from must not be able to change it, and the refusal is `:not_found` (identical to a record that isn't there), never `:unauthorized`, which confirms it exists. Judge it on the row the transaction locked, not on the id/name the caller passed, and BEFORE any state guard, or the denial leaks the state (`:not_trusted` told a stranger the version was trusted). Re-read the access at the mutation boundary so a scope narrowed mid-session takes the decision away from an already-open page. **An identity in an error message is in scope too:** narrow the names a failure reports to the ones the caller could already list (`Runners.reachable_scope_values/2` is the one definition), and let the copy drop the clause when none remain. Sweep: a `Repo.fetch_and_update`/lock helper carrying only `Authorizer.for_subject/2` where the sibling list also applies a scope filter; state guards (`:not_trusted`, `:not_pending`) that run before the scope guard; and error tuples carrying runner/member/host names assembled account-wide.
- **A privilege that can WIDEN a member's own reach requires the whole dimension, not just the verb permission.** An enrollment key is the case: the enrolling host self-reports its group, so any key is a fleet-wide grant and a runner-scoped member minting one lands a machine they control in a group they don't. Gate creation on the permission AND `mode: :all` (`Runners.subject_can_install_runners?/1`, `subject_can_create_enrollment_keys?/1`, `subject_can_manage_inactive_retention?/1` — all read access fresh, never from the session snapshot). NARROWING verbs (revoke, disable, delete, list-to-audit) keep the plain permission — taking capability away is safe at any reach, and removing the list would remove the only place the widening artifact can be revoked. Sweep: a create/mint/enable verb whose artifact is honored fleet-wide but is gated on a permission alone, and any account-wide schedule or sweep armed by a scoped member.
- **A database lock needs a realistic conflicting writer, not a theoretical interleaving.** Keep row locks at established state transitions where two ordinary writes can contend for the same record; do not wrap discovery reads or unrelated authorization checks in transactions merely to make them atomic against a deliberately coordinated membership, group, or catalog change. Re-read access at the actual mutation boundary and refresh mounted UI through the existing invalidation path. Sweep: `FOR SHARE` around lists, transactions whose only purpose is an authorization snapshot, and tests that need barriers or injected delays to manufacture the race.
- **A detail route stays about the selected record; a confirmation keeps its exact decision artifact beside the submit.** Put recent history and short guidance on the parent/index or start surface, never below an individual execution. Sweep: detail pages with sibling-history lists, confirmation plans displaced into rails, duplicate stage headings/strips, raw-output-only links with no inline result, result rows that abandon the plan grammar, repeated execution arguments, terminal cards, collapsed terminals, reconstructed commands, and authored Markdown rendered naked or on tinted cards. Worked example: `.agent/kb/rules/design-detail-routes-focus-on-current-record.md`.
- **Compact verdict labels in fixed tracks do not wrap, and peer verdicts share one width** — reduce padding before shrinking type, and verify at the narrowest grid breakpoint. `design-console-ux.md` §7.41.
- **A control's geometry belongs to its component: a caller's FACE never resizes its BOX** — `input_size/1` pins the line box, so `class="text-xs"`/`font-mono` restyles the text without shortening that one control out of its row. A trailing icon beside compact fields keeps the shared 40px target, uses the compact 32px face, reserves the full 2.5rem track, and centers on the control box; `h-8 w-8` cannot override `min-h-10 min-w-10`. `design-console-ux.md` §7.54.
- **A state change never moves the layout — and what must not move is the neighbouring CONTENT, not every control inside its own cluster** — view-only/plan-gated/disabled restyles in place, and a row's conditional trailing controls put the whole role+action CLUSTER in one fixed/minimum track with its members content-sized and right-anchored inside it (never a fixed track per control, which stretches a read-only value into a disabled-looking slab and strands a button-less row's pill mid-column). `design-console-ux.md` §7.55.
- **A trailing control track reserves its widest regular state, not speculative air.** Keep its right edge stable and let a genuinely wider exceptional cluster grow; an oversized minimum clips the neighbouring identity or metadata while visibly empty space sits before the controls. Sweep: fixed/minimum role-and-action tracks whose ordinary rendered controls leave enough unused width to complete the adjacent line. `design-console-ux.md` §7.55.
- **A roster row separates lifecycle metadata from exceptional state.** Keep identity and durable markers on the title line; render a pending invite as `invited … · pending` metadata, not `joined … · never active`. The `invited` timestamp already names the lifecycle, so the unresolved `pending` value may be amber for scanability, but gets no dot or separate warning line. Put real account/access cautions on separate compact lines beneath it. Render `access suspended` as lowercase amber metadata without a dot and keep its muted manager attribution inline; retain the amber marker for `Email unconfirmed`. Never dim the parent row for one state—opacity changes every semantic color beneath it. Sweep: invitation rows with amber pending markers or separate status lines, pre-acceptance joined/activity copy, adjacent same-tone caution chips, ambiguous combined caution prose, uneven status-stack rhythm, and state-driven opacity on the whole row. `design-console-ux.md` §7.62.
- **A native select reserves room for its chevron** — our `px-*` overrides the forms plugin's `padding-right`, so the longest option prints over the arrow; shared controls carry `select_chevron_room/1` and a hand-rolled select spells the padding out. `design-console-ux.md` §7.56.
- **A grid inside a rail-narrowed column keys its columns to the CONTAINER, not the viewport** — `@container` + `@md:`/`@2xl:`, and verify at the width where the rail first appears. `design-console-ux.md` §7.57.
- **Forms reveal before they validate, and conditional branches stay visually attached to their trigger.** A `phx-change` render never reports a required-value error for a field the operator hasn't filled — a change event carries EVERY field, so `Map.put(changeset, :action, :validate)` in a change handler accuses them of every blank they haven't reached (picking a provider put "can't be blank" under Issuer URL before the cursor had been in it). Worked example: `../.agent/kb/rules/design-conditional-form-branches.md`.
- **A completed workflow step replaces its form, and numbered steps stay contiguous.** After a successful submit, render the result as that step's completed state instead of stacking it above a reset form; never show step 2 without a visible step 1. Sweep: success assigns rendered beside their source `<.simple_form>`, and conditional `step={2}` sections whose preceding step is absent in any reachable state. Worked example: `.agent/kb/rules/design-completed-steps-replace-forms.md`.
- **Confirmation friction follows the resource's current consequence, not only the action noun.** A usable agent key is a live credential, so revoke stays typed; once it has expired and cannot authenticate, revoke is cleanup and uses the plain destructive modal. The server-side authorization, scoped fetch, audit, and mutation stay identical. Sweep: typed confirms on already-inert resources. `design-console-ux.md` §5.
- **Hierarchy rails meet control borders, never pass beneath or compete with controls.** A parent-to-child tree aligns its trunk to the parent checkbox center, touches that control, branches horizontally to each child checkbox's near border, and stops at the final child instead of dangling below the hierarchy. Worked example: `../.agent/kb/rules/design-hierarchy-rails-meet-control-borders.md`.
- **Compound identities use visual hierarchy when the field has vertical room** — accountable person on the first line, credential/client/channel muted on a second; never force `person via credential` through one truncating line. `design-console-ux.md` §7.11.
- **Dense entity facts use one aligned spacing grammar** — one label track, type tier, line height, and row gap for every secondary fact; copy/icon buttons fit inside the row height. `design-console-ux.md` §7.12.
- **A compact label/value fact starts on one row at every width.** Keep the label in its shared max-content track and let only the value column wrap; never force a short value below its label merely because the container crossed a breakpoint. Sweep: mobile `grid-cols-1` switches around dense facts whose label plus ordinary value visibly fit together. `design-console-ux.md` §7.63.
- **A flat picker past about a dozen options partitions by the kind the operator already knows.** Labeled subgroups (terminal agents vs editors/desktop apps) in the quieter subgroup-label tier; the shared fact stays once on the parent; popularity order within each subgroup derives from the ONE master list. Sweep: `:for` chip/tab clusters rendering > ~12 options flat. `design-console-ux.md` §7.66.
- **A section header's trailing action links ride the meta line, not the title line.** With a title+subtitle stack on the left, the trailing links bottom-align with the subtitle (`items-end`), leaving the title its full row. Sweep: `justify-between` header rows pairing a title+subtitle stack with `items-start`/`items-baseline` trailing links. `design-console-ux.md` §7.65.
- **A picker of named third-party things orders by popularity, not the alphabet or the order we shipped them.** Operators scan a client/provider/vendor picker for THEIR name, and most read only the first row of tabs — so the common choices go there and the long tail falls off the end. Keep the ids in an ordered list (a map's iteration order is not the render order) and comment that the order is popularity, so nobody "tidies" it back. Reference tables and sortable columns are exempt. Sweep: option lists rendered from a literal whose order matches the alphabet or `git log`. `design-console-ux.md` §7.64.
- **Mixed-density table rows align the scan line, then preserve hierarchy** — `items-start`, one primary metric pair, one secondary pair; alignment comes from the common top edge, not from making every column equally loud. `design-console-ux.md` §7.13.
- **A leading status marker centers on the primary text line**, not the whole content stack — derive its offset from the primary line box. `design-console-ux.md` §7.17.
- **A hit-area minimum is reserved outside the flow — it never sets the line box its row aligns to.** `min-h-10` on an inline control makes a 20px text row 40px tall, so a leading marker offset for the text (§7.17) floats above it; hang the target off the flow with a matching negative margin (`-my-2.5 … min-h-10`) and confirm icon, label, and control share one measured center. `design-console-ux.md` §7.67.
- **Transient recovery states do not borrow error semantics** — an automatic reconnect or retry is neutral; rose and failure copy are for terminal or actionable failures. `design-console-ux.md` §7.18.
- **Informative content wears a neutral tone; amber/rose is reserved for a warning or a decision** — identity, hashes, IDs and versions are `zinc`; a compound identity uses `<.identity_tag>`, and a container never repeats a status its items already carry. `design-console-ux.md` §7.42.
- **Casing is a style, never a value transform** — an identifier renders as authored; uppercase is a CSS class at eyebrow metrics, never `String.upcase/1` on a value reaching a template. `design-console-ux.md` §7.37.
- **A fact an action consumes rides that action's label, never a status chip beside the title.** The runbooks list said `Live v1` in a chip AND offered `Run` — the version belongs on the button that uses it (`Run v1`), and the chip goes. A secondary waiting-state signal (unpublished changes, pending sync) is quiet chrome: a toned `status_dot` inside the shared `<.tooltip>` with an accessible name, never a labeled badge shouting beside the identity. Sweep: list rows pairing a status chip with an action button that consumes the same fact, and labeled chips for secondary waiting states an operator only needs on approach.
- **A readiness panel narrates the action it currently gates, and its verdict is a plain fact, never a coined phrase.** One validation can serve two modes — shipping a pending change and re-checking what is already live — and its header, verdict, and blocked wording follow the mode: `Publish check / Ready to publish / blocks publication` only while a change is pending; a clean published runbook reads `Run check / Validated / blocks new executions`, with the body stating the capability directly ("This definition resolves and can be executed against current runners, trusted packs, action contracts, and policy."). A verdict label is a boring past-participle fact (`Validated`), not invented narrative ("Runs on current infrastructure", "still resolves"). The tell: a panel pitching an action the adjacent button reports as unavailable ("Make a change before publishing a new release"). Sweep: readiness/verdict panels whose copy hardcodes one action story across lifecycle states, and verdict titles that coin a phrase where a plain fact word exists.
- **A label:value detail row earns its place only when the value carries information** — render it conditionally, never as an `—`/`(none yet)` placeholder, never as the label's synonym (`Draft: Unpublished changes` said one thing twice; the row worth having states the consequence in the sibling rows' grammar — `Next: v2` beside `Live: v1`, matching the Publish button's own label), and use the shared `code_line` for a copyable value. Sweep: kv rows whose value restates or paraphrases its label. `design-console-ux.md` §7.43.
- **A command snippet shows only what the operator must actually type** — verify the CLI first: no default-valued flags, no step the tool already does, and pin the hash in the command rather than beside it. `design-console-ux.md` §7.44.
- **A command the operator must RUN is a copyable value, never prose inside the sentence.** The sentence says to run *the command* and the shared `code_line` carries it — including inside a tooltip, where `<.tooltip command={…}>` puts that row in the bubble (the revealed bubble is pointer-interactive and the clipboard listener is delegated at the document, so Copy reaches a control that exists only on hover). Spelled into a sentence, a command cannot be copied and wraps mid-token — the founder reported exactly that on the runner-update tooltip ("Run / sudo emisar update on this host"). A surface that states the same command twice keeps ONE spelling in a module attribute, so a row tooltip and its page notice cannot drift. Sweep: sentence strings in `lib/` carrying a shell verb (`sudo `, `emisar `, `curl `, `systemctl `, `journalctl `) outside a `code_line`/`code_panel`/`inline_code` value.
- **A command row's label says what to DO with it, not where the reader is standing.** `Run on the host`, `Install on a host` — an instruction the operator can act on. A bare prepositional phrase (`On the runner`, `On the host`) names a place and leaves the verb to be guessed, and it read as filler chrome above the one thing in the box that matters; the founder flagged exactly that ("content needs to be human friendly not like 'on the host' blah"). A label that names the CONTENT of a non-runnable value keeps its noun — `Executed command`, `Payload`, `Enrollment key` are describing what you are looking at, not asking for an action. Sweep: `code_line`/`code_panel` `label=` values that are prepositional phrases, and any command label with no verb.
- **Recovery feedback must cover the common interruption**, not only long outages — tune the grace period below the ordinary tab-resume reconnect, or the notice is functionally absent. `design-console-ux.md` §7.19.
- **Onboarding completion is capability-based, not connection-based** — a connected integration counts only when it exposes the capability the next step needs; never route an operator into an action that cannot succeed. `design-console-ux.md` §7.45.
- **Page-level attention has one slot, one surface, and one spine grammar per issue** — notices group after the intro and before counters/filters, row-level alerts use `<.event_block>` too, and a notice owns its command inside the same spine; on a posture overview (the dashboard) the stat row leads and the attention stack follows the numbers. `design-console-ux.md` §7.46.
- **Per-row admin verbs: 1-2 = small bordered buttons; 3+ = the Actions menu** — and a visible action button always wears a bordered face; `:ghost` is for menu rows and inline dismiss only. `design-console-ux.md` §7.47.
- **An overlay opens inward from the nearest canvas edge, and no ancestor may clip one away** — no room below the trigger means the panel opens ABOVE it, a panel past a canvas edge slides back inside, and a single-axis `-hidden` is never how an ancestor clamps overflow: `overflow-x-hidden` makes CSS compute the other axis to `auto`, so the work canvas became a scroll container that swallowed an open dropdown panel on the last row whole — the document never grew, so no scrolling reached it. Use `overflow-[xy]-clip` for one axis; `assets/js/overlay.js` owns the shared canvas bounds so the tooltip bubble and the dropdown panel cannot drift. **Enforced** by `EmisarWeb.TemplateHygieneTest` + `EmisarWeb.Components.DropdownTest`. `design-console-ux.md` §7.25.
- **Spacing utilities require element siblings** — wrap prose in `<p>` before relying on `space-y-*`; raw HEEx text nodes do not participate in the sibling combinator. `design-console-ux.md` §7.22.
- **`whitespace-pre-wrap` content glues to its tags via a one-line inner span** — template indentation inside a pre-wrap element renders as real leading whitespace. `design-console-ux.md` §7.48.
- **Inline link/anchor text glues to its closing tag when punctuation follows** — `}>text</.link>.`, never the formatter's loose `>` ⏎ `text` ⏎ `</.link>.`, whose newline renders as a visible space ("a shell ."). **Enforced** by `EmisarWeb.TemplateHygieneTest` — a test, not a Credo check, because Credo cannot parse `.heex`.
- **Every attention spine starts with a visible, semantically exact icon** — match the meaning to the operator action; a name the registry does not own now raises rather than shipping an invisible glyph. `design-console-ux.md` §7.49.
- **A note that instructs the operator wears the callout spine** — the spine-less `<.status_note>` is only for a passive posture fact about the surface. `design-console-ux.md` §7.50.
- **One metadata group has one value typography and tone contract** — peer values share size, line height, and tone; a copy button or mono ID does not invent hierarchy. `design-console-ux.md` §7.14.
- **An icon that carries unrepeated meaning always explains itself** — wrap it in the shared tooltip with an accessible name; decorative icons stay hidden from accessibility. `design-console-ux.md` §7.15.
- **Relationship eyebrows lead with the variable entity kind, not the fixed role** — `USER · ACTOR`, kind first and brighter. `design-console-ux.md` §7.16.
- **Scheduled housekeeping matches the precision of its promise and never replenishes itself.** A day-based retention policy sweeps daily, not hourly, so its audit summary does not dominate an inactive account. A cleanup job may delete its own expired summary markers, but those markers do not count as operator-meaningful work and must not trigger or inflate a replacement marker. Use the delete's returned rows to count what was actually removed, and cover the inactive-account marker-only sweep so scheduled housekeeping cannot manufacture permanent audit noise. **A retention sweep judges liveness from durable peer state, never from an event-driven timestamp alone:** a `last_seen_at` that only refreshes when the peer re-sends state (runner_state on reconnect/SIGHUP/pack change, not on a timer) goes stale on a healthy, connected peer — so a sweep keyed on that age must also exclude rows a durably-connected peer still references (the pack-retention sweep reads connected runners' `packs` maps inside its transaction; the retired-version bookkeeping, which has no age window at all, reads every non-deleted runner's `packs` map, offline hosts included). Sweep: retention queries whose only predicate is an age comparison on a state-advertisement timestamp.
- **UI copy stands alone on the surface it renders on — never an answer to a question that isn't there.** "Yes - masked in plans, approvals, and results." as a section subtitle is leaked review dialogue: an agent answered a question and pasted the answer over the sentence it was asked about (and pinned it with a test, so the suite asserted the defect). Every rendered sentence must read complete to an operator who arrives cold; an answer fragment is legitimate only where its question is on the same surface (a table cell under its column header, an FAQ answer under its question). Sweep: `Yes/No/Correct [—-]` sentence openers in `lib/` templates outside tables and FAQs — and when copy changes, re-read the SURROUNDING surface, not just the diff line.
- **A paragraph in a plain-text email body is ONE line, however long.** Newlines in a `text_body` are structure only — a blank line between blocks, a code or URL alone on its line, an indented two-space `Label:` block. A mail client re-wraps a long line to the window it has but can never undo a newline we sent, and a source wrap around an interpolated value breaks at a column the reader never sees: `#{inviter.full_name || inviter.email} invited you to join the` ⏎ shipped an invitation that broke 36 characters in. **Enforced** by `Emisar.Mailers.TextLayoutTest`, which renders every email we send and asserts each prose line both starts and ends a sentence — add a new email to its `bodies/0`. Sweep: any multi-line prose paragraph in a string reaching `text_body`. Worked example: `.agent/kb/rules/content-emails-keep-a-paragraph-on-one-line.md` (repo root).
- **Marketing copy must sound spoken, not generated.** Lead with the concrete behavior an operator recognizes. Avoid abstract-noun labels, mirrored slogan headlines, sentence-fragment drumbeats, fake precision, and formatting that tries to supply a voice. Read it aloud; if one operator would not say it to another, rewrite it.
- **Plan entitlements name the concrete channel or deliverable, not a qualitative service level.** Say `Email support`, `Dedicated Slack support channel`, or `Rollout support`; never leave a buyer to interpret an undefined label such as `priority support`. Sweep support claims across plan cards, comparison tables, and plan summaries together so the same tier makes one promise everywhere.
- **Product comparisons stay at the same level of detail.** Compare the operator's work on both sides; never put a simple user action beside the product's internal machinery and make the product look like extra steps. Put technical proof below the outcome. State one-time setup together with the repeated payoff, not as a standalone warning that argues against buying.
- **One sales argument uses one container and hierarchy.** Do not split an objection, recommendation, and payoff across neighboring sections with different widths or equal headline weight. Keep the exception quiet, make the recommended path dominant, and place setup beside the value it unlocks.
- **Marketing pages choose one visual grammar before polishing sections.** Establish one content canvas, section rhythm, semantic color roles, proof treatment, and mobile density for the whole page. A collection of individually polished components that changes composition without narrative reason is not coherent design; review full-page desktop and mobile screenshots, not only section crops.
- **The marketing hero is one treatment, sourced from the `marketing_heading` scale — never a per-page `!text-*` override.** Every primary/top-nav page (home, security, pricing, about, zero-trust, docs, changelog, how-it-works, trust, guides, use-cases, packs) opens identically: `scale={:display}` with size + leading living IN the scale, `py-24 sm:py-32` section padding, `text-base` eyebrow, `max-w-2xl` lede. Worked example: `.agent/kb/rules/design-marketing-hero-scale.md`.
- **A CTA arrow rides in the text flow after the last word, glued by `&nbsp;` — never as a flex sibling of its label.** `inline-flex items-center` makes the label and the arrow two flex items, so a label long enough to wrap leaves the arrow floating mid-air at the block's right edge (the founder reported exactly this on two home-page section CTAs at phone width); a plain space before the arrow is a line-break opportunity that strands it on its own line. Marketing CTAs go through `<.cta_link>`, which owns the glue AND the one treatment — the wrapper owns spacing/alignment, a section CTA centers under its section, and a link carrying its own `mt-*` needs `inline-block`. **Enforced** by `EmisarWeb.TemplateHygieneTest` (marketing-scoped: console nav CTAs are short fixed labels that cannot wrap). Sweep: `inline-flex items-center` on a link whose label is a sentence, and every `<.icon name="hero-arrow-right">` or literal `→`/`&rarr;` inside a link. `design-system.md` §4.
- **Docs prose pages share one vertical rhythm through `docs_components` — never inline ad-hoc typography.** A `/docs/*` prose page renders through the shared shell and inherits: `text-base` (16px) body copy (no `text-sm`/`text-xs` drift — 14px on a wide column reads dense), a measure capped at `max-w-2xl` by `docs_layout` (code/tables/figures fit inside it, so every block shares one left edge), one line-height (`docs_layout` pins `[&_p]:leading-7 [&_li]:leading-7` = the right 1.75 ratio on 16px, so don't fight it with inline `leading-6`/`leading-8`), one block gap (paras + `docs_code` `mt-5`, callouts `mt-6`, `docs_h2` `mt-12`, `docs_h3` `mt-8`), and prose list items at `space-y-3` — never `space-y-{1.5,2,2.5}`. Sweep: body `text-sm text-zinc-400/300` (non-mono), `<[uo]l>` at `space-y-{1.5,2,2.5}`, inline `leading-*` on body text, or a page setting its own wider `max-w-*`. Worked example: `.agent/kb/rules/design-docs-prose-rhythm.md`.
- **Workflow guides show every decision-bearing surface; an overview crop never substitutes for controls below the fold.** Teach complex editors in task order and put a focused screenshot or complete canonical example beside each field group that changes the result. Worked example: `../.agent/kb/rules/content-workflow-guides-show-decision-surfaces.md`.
- **One-line copy values are compact controls, not code panels** — one short row, no internal scrollbar; clip the preview and let Copy carry the full value. `design-console-ux.md` §7.28.
- **Do not label state already obvious from the action** — a card whose sole action says `Turn off` needs no `On` label. `design-console-ux.md` §7.29 and §7.31.
- **"Managed by <provider>" is stated once at the row, never repeated per attribute** — the provisioning badge plus a lock on each inline-editable control says it; a read-only value gets no FYI. `design-console-ux.md` §7.51.
- **Copy actions do not repeat an obvious artifact noun** — `Copy`, not `Copy command`, unless adjacent targets must be distinguished. `design-console-ux.md` §7.30.
- **An unlabeled dot represents only one unambiguous status** — never put an enabled/disabled dot beside metadata reporting a different dimension. `design-console-ux.md` §7.32.
- **Setup reassurance is short and operational** — one plain sentence on why it is safe, one on where to change it. `design-console-ux.md` §7.33.
- **Transport diagnostics never render as customer copy** — map abnormal socket/process values to one stable sentence; keep tuples and inspected exceptions in logs. `design-console-ux.md` §7.34.
- **Composite metadata values are never clipped by scalar truncation** — a value carrying a badge or control opts out of single-text `truncate` and wraps as a unit. `design-console-ux.md` §7.35.
- **A result summary stays with the collection it quantifies** — filter/search feedback sits beside the rows, never joined by middots into durable entity metadata. `design-console-ux.md` §7.36.
- **A content hash or machine id reaches the view in FULL; the container fits it** — pass `"sha256:#{sha}"` and let the surrounding `truncate` + `title` ellipsize only when narrow, so it reads whole where there is room. An inline slot with no truncating wrapper of its own (a disclosure `:summary`) gets `min-w-0 truncate` + a full-value `title`. **Credo-enforced** (`Emisar.Checks.NoHashPrefixSlice`).
- **A repeated inline element (`<.chip>`, badge, pill) rendered by a comprehension lives in a `flex flex-wrap` container**, never loose in a text-flow parent — the lead-in prose goes in its own element, and the container's gap replaces any per-chip `ml-*`. Only visible at real data volumes, so verify the widest list. **Enforced** by `EmisarWeb.TemplateHygieneTest`.
- Pipe into the data; don't nest calls. A function reads top-to-bottom as a pipeline (`Query.not_deleted() |> Authorizer.for_subject(subject) |> Repo.list(...)`).
- Keep a pipeline's anonymous-function steps visually uniform: if any step's `fn` must wrap (body and `end` on their own lines, because it's too long to inline), hand-wrap the short ones too rather than leaving them inline. `mix format` preserves a hand-wrapped short `fn`, so the whole `Multi`/pipeline reads as one shape instead of a ragged mix of inline and block closures.
- `with` for the happy path; let the `else` carry the error shapes. Don't pyramid `case`. Prefer one flat `with` over a `case` whose branch opens another `with` — fold the inner steps up as more `<-` clauses.
- No multiline pipe in the *head* of a `with`/`case`/`if` clause (the expression being matched). If it needs `a |> b |> c` across lines, bind it first — a `name = expr` step inside the `with`, or a line above — and match the short name. `with {:ok, u} <- %X{} |> Changeset.f(attrs) |> Repo.insert() do` spanning three lines is a readability tax; `with cs = Changeset.f(%X{}, attrs), {:ok, u} <- Repo.insert(cs) do` reads flat. The same goes for a multiline pipe **as a function-call argument** (`Multi.delete_all(:tokens, A.x() |> A.y())`) — bind `queryable = …` before the call or pass a `fn changes -> … end` whose *body* pipes.
- A `, do:` one-liner is for bodies that FIT on one line. If the formatter would wrap `do:` onto its own line (the body spills over 98 cols), write a regular `do … end` block instead — `def f(x),\n  do:\n    long_call(…)` is never acceptable output. **Credo-enforced** (`Emisar.Checks.MultilineDoColon` flags any source line that is a bare wrapped `do:` — `def`/`defp` bodies and inline `if/unless` alike).
- Never bind a literal tuple just to re-return it (`{:error, :invalid} = err -> …; err`). Restate the literal at the end (`{:error, :invalid} -> …; {:error, :invalid}`), or for a wildcard pass-through re-wrap the bound reason (`{:error, reason} -> {:error, reason}`). The binding hides what the function returns.
- Name by intent, not by type. `expire_overdue_requests`, not `update_requests`. Boolean-returning fns end in `?`.
- Return only the shape callers consume. Don't carry an extra map field or a `{entity, flag}` tuple (e.g. fetch-or-create's `{user, created?}`) that no caller branches on — it's noise every caller and test must destructure, and it complicates the function. Confirm a real consumer exists before adding a return field; drop it when the last one goes.
- Spell variables out: `changeset`, not `cs`. A struct-typed binding takes the schema's own name — `%Membership{} = membership`, not `m`/`target`. Reach for a qualified name (`target_membership`) only to disambiguate two bindings of the same type.
- **The discard form depends on the layer — `_ = expr` belongs in `lib/`, not a test arrange.** In `lib/`, `_ = expr` is the GOOD, explicit signal "this returns something and I'm dropping it on purpose" — keep it; a bare `expr` statement can read as a forgotten return. In a TEST body, a fixture/side-effect setup call IS the statement: write the bare call — `Fixtures.Memberships.create_membership(account_id: …)`, not `_ = Fixtures.…` — or a descriptive `_name` (`_owner_membership = …`) when the name documents the unused row; a bare `_ =` there neither names the thing nor reads as setup. (Either layer: a context-API `{:ok, _}` is **asserted**, not discarded — `{:ok, _} = Accounts.suspend_membership(…)` — so a failure can't pass silently; and `_ = some_var` to quiet an unused-variable warning is a smell, rename the binding `_var` at its source or it's dead code.)
- **Sibling bindings of the same kind follow ONE naming scheme.** When a test (or function) creates two-plus values of the same type, name them by a single scheme — all by role/descriptor (`owner_membership`, `_other_membership`), all `_a`/`_b` suffix matching their accounts (`membership_a`, `membership_b`), or all spelled ordinals (`membership_one`, `membership_two`, `_membership_three`) — never mix a descriptive name with an ordinal (`owner_membership` then `_second`), and never drop the shared prefix on one (`m_one`, `m_two`, then `_three`). The reader pairs siblings at a glance; a mixed scheme reads as two unrelated things. (Spotting this needs the whole file in view, not a grep — see the related working rule.)
- Pattern-match struct arguments by their struct in the function head — `create_request(%Runs.ActionRun{} = run, …)`, not a bare `run`. The head documents the contract and guards the type.
- Reference **another** context's modules through its top-level alias — `alias Emisar.Runs` then `Runs.ActionRun`, never `alias Emisar.Runs.ActionRun`. It keeps obvious which context a schema belongs to. (Aliasing your *own* context's submodules — `Grant`, `Request` — directly is fine. `Emisar.Auth.Subject`, the universal auth carrier, is the one cross-context exception we alias directly everywhere; `Emisar.Repo.*` is infra, not a context.) Applies to the web app too — a LiveView aliases the context, not its schemas. **Credo-enforced**, path-aware (`Emisar.Checks.CrossContextDeepAlias` derives the file's own context from its directory and flags any other `alias Emisar.<Ctx>.<Sub>`).
- **The web is an ADAPTER, so every call it makes lands on a top-level context.** `apps/emisar_web` calls `Emisar.<Context>.fun(...)` and never a module beneath one — not `Catalog.PublishedRegistry`, not `Accounts.RunnerAccess`, not `Runbooks.Authoring`, not a `<Schema>.Query`/`<Schema>.Changeset` — and never builds or mutates an `Ecto.Changeset` (`add_error`, `cast`, `change`, `put_change`, `validate_*`, `*_constraint`, `apply_action`, `apply_changes`). Worked example: `.agent/kb/rules/elixir-web-is-an-adapter.md`.
- **A context's `<Schema>.Changeset` modules are write-internals — no sibling context builds them.** Another context never does `User.Changeset.x(...) |> Repo.update()` or `Multi.update(:user, User.Changeset.x(...))`: it calls a (possibly `@doc "Internal"`) function on the owning context, composing it into its transaction via `Multi.run(:user, fn _repo, _ -> Users.mark_user_confirmed(user) end)` — same atomicity, internals stay private (this is how Auth's token flows write user rows). **The same goes for cross-context READS**: a sibling never builds a full pipeline on another context's `<Schema>.Query` + `Repo` (billing counting memberships, approvals fetching a run) — the owning context exposes the (often `@doc "Internal"`) function (`Accounts.count_memberships/1`, `Runs.peek_run_by_id/1`, `Runners.runner_active_in_account?/2`). The **sanctioned exceptions**, all documented elsewhere in this file: struct pattern-matches and pure schema helpers (`User.valid_password?/2`); Query-module *composition* — joins (`with_joined_user`), the audit label/scope resolvers (§2's `select_labels` + `Audit.resolve_references`); context-owned `jobs/*` consuming Query-built pipelines (IL-1 prescribes it); fixtures/seeds building rows directly (§7). When a query module joins another context's table, it composes that schema's `Query.not_deleted()` (`m in ^Membership.Query.not_deleted()`), never the raw schema module — a raw join leaks soft-deleted rows.
- One public function = one job. If a context function has an `opts` flag that changes *what it does* (not just filtering), it's two functions.
- Recurrent jobs use the Firezone-style pattern: domain jobs live under the owning context's `jobs/`, and that context module supervises them. `Emisar.Jobs` is infrastructure only (declaration macro + executors) — do not put business sweep engines in top-level `Emisar.Jobs` or recreate `lib/emisar/workers/`.
- Small modules over big ones, but never a module per function. Follow the standard split (context / schema / query / changeset / authorizer) and stop there.
- Comments explain *why*, never *what*. The code says what. If you're tempted to narrate the what, the code isn't readable enough yet.
- All `use` / `import` / `alias` / `require` go at the very top of the module, **in that order** (`use` → `import` → `alias` → `require`) — never inside a function body or partway down the file. No blank line between `@moduledoc` and that block, **and none between the directives** — the module header is one contiguous block (`require Logger` sits at the bottom of it, after the aliases, not up by the moduledoc). **Credo-enforced** — the order is `StrictModuleLayout`; `Emisar.Checks.NoBlankBetweenDirectives` flags a blank line sandwiched between two directives, with ONE exception it skips: the blank `mix format` itself inserts before a multi-line directive whose options wrap (`use Phoenix.VerifiedRoutes,` ⏎ `  endpoint: …`) — don't fight the formatter there.
- **A grouped alias (`alias X.{A, B, C}`) stays on ONE line** — when the group outgrows one line, split it into several single-line grouped aliases, never the formatter's one-module-per-line block. Each split line fits, so `mix format` leaves it alone. **Credo-enforced** (`Emisar.Checks.MultilineAliasGroup`).
- Existence checks use `Repo.exists?(query)`, never `Repo.aggregate(query, :count, :id) > 0` — and never a fetch used only to test presence (`case fetch_x(…) do {:ok, _} -> taken` is the same violation: it pulls the whole row to answer a boolean). `exists?` stops at the first matching row.
- Enforce uniqueness with a DB unique index + `unique_constraint` in the changeset + error mapping — not a read-before-write check (`peek`/`exists?`-then-insert) inside the transaction. SELECT-then-INSERT races under concurrent callers (TOCTOU); the (partial, soft-delete-aware `WHERE deleted_at IS NULL`) index is the source of truth. Let the insert hit it, then map the constraint changeset back to the domain error (`%Ecto.Changeset{data: %Membership{}}` + a `:unique` error → `{:error, :already_member}`) — the unique-error test is the shared `Emisar.Repo.Changeset.unique_constraint_error?/1`, never a per-context private copy.
- Writing N rows? Use **one** `Repo.insert_all`/`Multi.insert_all`, not a `Multi.insert` (or `Repo.insert`) per row — especially for simple join tables. `insert_all` skips changesets, so validate first (build the changesets, bail on the first `not valid?`, then `insert_all` their `.changes`) and supply what it won't autogenerate: `:id` via `Repo.generate_id/0` (UUIDv7) and `:inserted_at`. The DB still backstops (`CHECK`, `varchar` length, unique index). The exception is a *deliberate* per-row insert/upsert for error isolation (one bad row mustn't abort the batch, e.g. the catalog action observe) — document why.
- `Repo.valid_uuid?/1` already returns false for `nil` and non-binaries — gate an id-fetch with a bare `if Repo.valid_uuid?(id)`, no `is_binary` guard (or nil clause) in front of it.
- **A single-row read returns `{:ok, row} | {:error, :not_found}` via `Repo.fetch(query, Query)`** — or `repo.fetch(query, Query)` inside a `Multi.run` — **never** `Repo.one()`/`repo.one()` followed by a hand-rolled `if row, do: {:ok, row}, else: {:error, :not_found}`. That nil→tuple is exactly what `Repo.fetch/2` replaces; reach for `Repo.peek/1` only where `nil` is itself the answer (§1.1). And **name a function for what it returns, not one side effect along the way**: a row-returning read is `fetch_*` (the prefix IS that tagged-tuple contract), one that mutates *and* hands the row back spells out both jobs (`fetch_and_lock_*`), and a side-effect-only name (`lock_*`, `touch_*`) must never secretly return a row a caller consumes. Sweep: any `one()`/`peek` paired with a `{:ok, _}` / `{:error, :not_found}` nil-check, and any side-effect-named fn returning `{:ok, struct}`.
- **A read/lock/write helper built to compose into a caller's `Ecto.Multi`/transaction takes the transaction repo as an optional** — `Keyword.get(opts, :repo, Repo)`, passed `repo: repo` from a `Multi.run` so it joins the open transaction, defaulting to `Repo` for standalone use. `repo` is genuinely optional, so it lives in `opts`, never as a positional (cf. *always-present arguments are positional*). Such a shared helper also **can't require a `%Subject{}`** if any caller is a subject-less system path (recurrent job, runner self-registration) — scope by the explicit, already-authorized `account_id` per §5, not `Authorizer.for_subject/2`.
- **A `Multi.run` callback's `repo` is a *variable*, so every `repo.fetch/one/update/insert/delete/all(...)` is a dynamic call `mix compile --warnings-as-errors` can NOT arity- or existence-check** — a wrong-arity `repo.fetch(query)` (missing the `Query`-module arg) compiles clean and crashes only at runtime. Match `Repo.<fn>`'s real signature by hand, exactly as a direct call would, and `/tooling-verify-api` the arity even when the compiler stays silent. Sweep: every `repo.<fn>(` call site. (Review+grep — not cleanly Credo-checkable.)
- All crypto goes through `Emisar.Crypto` (`random_secret/1`, `hash/1`, `mint/2`, `secure_compare/2`) — never inline `:crypto.*` or `Base.url_encode64` for a secret/digest in a context. One module keeps the RNG, encoding, and hash algorithm auditable in a single place (a security product wants exactly one crypto review surface). A token's byte **length** is a crypto concern too: expose a named minter (`Crypto.user_invite_token/0`) instead of calling `random_secret(24)` with a literal length in the context.
- Seed data never enrolls MFA/2FA and never mints TOTP secrets or recovery-code digests. Seeds may confirm demo users and may clean up a previously-seeded MFA enrollment through `Auth.disable_mfa/1`, but screenshot data must not fake possession of a user's second factor.
- Field whitelisting is the changeset's `cast/3`, never a `Map.take`/`Map.drop` in the context. A mutation that may only touch a subset of fields gets its own changeset function (e.g. `User.Changeset.profile/2` casts only `full_name`); the context calls that, it doesn't pre-filter attrs.
- **A group of operator-tunable settings goes in ONE embedded `settings` jsonb value, not a column-per-toggle.** When a schema accumulates admin-flippable toggles/caps (booleans, limits, small enums), make them an embedded value object — `embeds_one :settings, <Schema>.Settings, on_replace: :update` over a `settings :map` column — that owns its own `changeset/2` (the embed is a plain `use Ecto.Schema` + `@primary_key false` module — the one place `use Emisar, :schema` doesn't apply, since it has no table/PK/timestamps). Worked example: `.agent/kb/rules/elixir-embedded-settings.md`.
- **Cast user input through the changeset FIRST, then read the cast value back for guards** — `changeset = X.Changeset.update(row, %{role: new_role}); new_role = Ecto.Changeset.get_field(changeset, :role)`. The Ecto.Enum cast hands you the atom (or an invalid changeset); a hand-rolled `normalize_role`/`cast_*` in the context duplicates the changeset's job and drifts from it.
- A read a transaction depends on goes *inside* the `Multi` as a `Multi.run` step (later steps read it from `changes`), not eagerly before `Multi.new()`. It stays in the transaction's snapshot and a missing row becomes `{:error, …}` instead of a raise.
- **Fetch-then-mutate holds the row lock.** Any function that looks a row up and then writes it (admin profile edits, forced password resets — not just self-service) goes through `Repo.fetch_and_update/3` (locked re-read + `:with` changeset + `:audit` + `:after_commit`), or fetches inside the `Multi`. Fetching with `fetch_user_by_id/1` *outside* the transaction and `Multi.update`-ing the stale struct loses concurrent writes between the read and the lock.
- A **fetch-or-create** must survive the insert race: insert with `on_conflict: :nothing` and re-fetch the winning row. A raw unique violation can't be rescued-and-continued inside the surrounding transaction (Postgres aborts it), so SELECT-miss → INSERT → re-SELECT is the race-safe shape.
- Compose transactions with `Ecto.Multi` + `Repo.commit_multi`, not `Repo.transaction(fn … end)` with imperative `case` / `{:ok, _} =` matches / `Repo.rollback`. A **fetch-or-create** is a single `Multi.run` that returns `{:ok, {row, created?}}`; later steps read it from `changes`. A reject condition (e.g. "already a member") is `{:error, reason}` from a `Multi.run`, not `Repo.rollback`.
- When one update path spans fields with different permission levels, build the (side-effect-free) changeset first, inspect `changeset.changes`, and require the permission matching the fields that actually changed — don't split into near-duplicate functions, and don't gate the whole path at the most-privileged level (that needlessly blocks low-privilege edits). The same shape applies when the required permission depends on a **value being granted** rather than a changeset field: inviting/assigning the `:owner` role needs `manage_owners` on top of `invite_member`, so pick the permission *list* from the role and run **one** `ensure_has_permissions/2` — not a permission check plus a separate role guard.
- Audit rows are built by **per-event helpers** in `Emisar.Audit.Events` (e.g. `account_created/2`, `membership_role_changed/3`) that take the domain structs + the acting `%Subject{}` and derive the actor (`Subject.actor_kind/1`, `Subject.actor_id/1`). Context mutations call those inside their `Multi.insert(:audit, …)`; they never hand-assemble `actor_kind`/`subject_kind`/`payload`. Add a builder per newly-audited event. **Audit is a domain concern: controllers/LiveViews never call `Audit.log*` — the domain function that performs the mutation writes its own audit row** (e.g. `Accounts.record_sign_in/2` owns `user.signed_in`; the session controller just calls it).
- **Request metadata (IP, user agent, request ID, MCP client metadata) is an `%Emisar.RequestContext{}` struct, threaded explicitly — never the process dictionary.** It rides on `%Auth.Subject{}.context` for authenticated callers, and is an explicit `context \\ %RequestContext{}` last positional argument on pre-auth paths (sign-in/out, magic link, password reset, email confirm, MFA verify). The web boundary builds it once — `EmisarWeb.RequestContext.from_conn/1`, or `from_socket/1` captured at **mount** because `get_connect_info/2` is mount-only. An event with no context carries no request metadata by construction. **Credo-enforced** (`Emisar.Checks.NoProcessDictionary`).
- **Runtime config a test (or dev) must override goes through the `Emisar.Config` seam, never `Application.put_env`.** Read with `get_env/3`/`fetch_env!/2` (a straight passthrough in dev/prod, so both read config identically); a test overrides with `put_override/3`, which is scoped to its own process and dies with it — which is what keeps those tests `async: true`. Mirrors Firezone's `Domain.Config`. **Credo-enforced** (`Emisar.Checks.NoApplicationPutEnv`, in `lib` and `test`).
- Errors are values (`{:error, reason}`), not exceptions, on any path a caller can hit. `!`-raising variants only behind a proven invariant.
- Don't wrap a single delegating call in its own named function — inline it. A `defp foo(a, b), do: Bar.foo(a, b)` earns a name only when it adds meaning the call site lacks; otherwise the indirection just costs a jump. Keep the *why* comment at the call site.
- A pure helper used in more than one place is its own small module with unit tests (e.g. `Emisar.Slug`), not a `defp` copy-pasted between call sites. Take options for the per-caller differences instead of forking the logic.
- **A constant used in ONE function is a local binding, not a module attribute.** `@x "…"` hoists a value to module scope and tells the reader "this is shared / module-level config" — earn that only when it's genuinely read by several functions or is module config (`@fields` cast list, `@create_fields`, a `@timeout`). A message or literal used in a single test/function is `x = "…"` right where it's used; a `@module_attr` read exactly once is misdirection — the reader scans the whole module for the other uses that don't exist. (The constant analog of the helper rule above: single-use → inline; multi-use → hoist.)
- **A guarded single-row mutation goes through `Repo.fetch_and_update/3`, not a hand-rolled lock-Multi.** Its `:with` runs inside the transaction on the locked row — bind that row `loaded_<schema>` (`loaded_account`, `loaded_membership`), never a vague `fresh` — so domain guards that must judge CURRENT state (hierarchy checks, field-aware escalations) live there — returning any non-changeset value aborts as `{:error, that_value}`, and an invariant query a guard needs (the locked last-owner re-count) is a plain `Repo` call, which joins the same transaction. `:audit` takes `(updated)` or `(updated, changeset)` — `changeset.data` is the locked pre-update row when the audit payload needs before-state (e.g. role changes). Hand-roll a `Multi` only when the mutation writes OTHER rows after judging the locked target (Accounts' `lock_target_membership/3` prefix) or spans multiple tables. **Composing `fetch_and_update` inside such a Multi is the intended shape** — its nested transaction JOINS the outer one, so both row locks + the audit insert commit atomically — but the nested call carries `:audit` ONLY: an `:after_commit` there would fire when the inner transaction returns, i.e. while the outer is still open, letting side effects escape a commit-time rollback. Side effects belong on the outer `Repo.commit_multi(after_commit: …)`; `fetch_and_update` raises on the nested misuse.
- `Authorizer.for_subject/2` is the **last** queryable transform in a pipeline: filters, ordering, preload helpers, and `lock_for_update` come before it, and the `Repo.*` call follows immediately. IL-4 says "immediately before" — that's the letter, not approximately.
- **Upserts are preferred.** When the row's identity is a unique key, write it with ONE statement — `Repo.insert(changeset, on_conflict: {:replace, [...]}, conflict_target: ..., returning: true)` — not peek-then-insert-or-update and not insert-rescue-refetch. The upsert is atomic under concurrency where the read-then-write shape races. When an audit payload needs the before-state, read it as a step in the same `Multi` — still a single write. (Exception: a state machine where the conflict path must *judge* the existing row — e.g. pack trust — keeps its explicit branches; say why at the call site.)
- **Use RETURNING instead of a follow-up read.** Data the write itself can hand back is never re-fetched: `returning: true` on insert/upsert, `select` on `update_all`/`delete_all`. A write immediately followed by a fetch of the same row(s) is the smell.
- **Dispatch on a pattern, not an inner `if`.** A closure or function whose body is one `if`/`case` testing a pattern-matchable property of its argument (field nil-ness/truthiness, a literal value, struct shape) becomes clause heads instead: a `:with` callback like "skip when already linked" turns into a named two-clause defp (`link_paddle_customer_unless_linked(%Account{paddle_customer_id: nil}, id)` / catch-all) passed by capture; a bare-arg `case` with literal branches (`client_config("cursor", url, key)`) turns into multi-clause heads. `if` stays for genuinely computed conditions (comparisons, function-call results) and `case` stays for matching something *other than* the argument itself (e.g. `conn.assigns[:x]` Access on optional keys).
- **`match?/2` answers a SHAPE question; it never disguises a plain field read.** `match?({:ok, %{require_sso: true}}, fetch())` goes **silently always-false** the day the field moves — that is exactly what disabled the `require_sso` last-provider guard when the field moved into the settings embed. Destructure the result with a `case` and read the field (`case fetch() do {:ok, settings} -> settings.require_sso; {:error, _reason} -> false end`). The same readability rule applies when the value is already guaranteed to be a struct: `access.mode != :none`, never `match?(%RunnerAccess{mode: mode} when mode != :none, access)`. A struct pattern remains right when the runtime type or nil-or-struct shape is itself the question; use an explicit `case` when the branch also returns different values. The bare-map defect is **Credo-enforced** (`Emisar.Checks.MatchOnMapFieldValue`); deciding whether a struct's shape is genuinely in question remains review judgment.
- **Any closure whose body is a single call uses capture syntax** — `&disconnect_user_sessions/1`, `&do_revoke(&1, id)`, `&save(&1, publish?: true)`, `audit: &Audit.Events.policy_updated(subject, policy, &1)`, `& &1.group` — so long as it stays one readable line. `fn` earns its keep only for: multi-step bodies, pattern-matching heads, multi-clause closures, a zero-arity closure that passes scope values (a capture needs at least one `&N` placeholder — `fn -> count_for(subject) end` can't convert; bare `fn -> f() end` becomes `&f/0`), a closure nested inside an outer capture (capture-in-capture won't compile), and when the argument is used several times and naming it genuinely reads better than repeated `&1`s.
- **Every PubSub publish goes through a named per-event function** — `broadcast_auth_key_revoked(%AuthKey{} = key)`, not a shared `broadcast_x_change(struct, "event.string")` that takes the event name as data. The function head documents the message; the literal topic + tuple live inside it. All `subscribe_*` and `broadcast_*` functions sit together in one `# -- PubSub ----` section per context so the context's topics and message shapes read in one place. No inline `Emisar.PubSub.broadcast/2` at mutation sites.
- **No pipe anywhere in a `with`/`case`/`for` head — single-line included.** `{:ok, x} <- a() |> b()` hides the operation being matched; bind first (`queryable = Token.Query.all() |> Token.Query.by_prefix(prefix)`) and match the short call (`<- Repo.peek(queryable)`). Credo-enforced (`Emisar.Checks.NoPipeInBranchHead` matches the AST, so every form — one-line, wrapped, `case` heads — is caught).
- **Preloads that exist for rendering are the CALLER's concern** — the context exposes a `preload:` option and maps it to the Query's `with_preloaded_*` helpers through a whitelist reducer, so a counting caller pays for no joins. Preloads that are the function's CONTRACT (every caller needs them) stay unconditionally chained with a why-comment. **Credo-enforced** (`Emisar.Checks.NoPreloadInRepoOpts`).
- Don't build an argument with a nested transform call inline — `Repo.fetch(query, Query, Keyword.put_new(opts, …))` makes the reader parse two calls at once. Bind the transformed value on its own line above, then pass the name. (Same family as the multiline-pipe-as-argument rule.)
- LiveTable `filters/0` callbacks bind their queryable as **`queryable`** — `fun: fn queryable, statuses -> …` — never `q`. (The `[runs: r]`-style DSL bindings inside `dynamic`/`where` stay the documented §2 idiom.)
- **A query DSL binding is a SINGLE letter** — `[group_members: g]`, not `[group_members: gm]`. The binding atom already names the table, so the variable is just a one-letter handle (the §2 idiom: `[runbooks: r]`, `[memberships: m]`); a multi-letter abbreviation is the same smell as `cs`/`q`. **Credo-enforced** (`Emisar.Checks.ShortBindings` flags multi-letter bindings in the 3-arg `where`/`order_by`/`select`/… forms).
- **`@doc`/`@moduledoc` state the contract, never narrate the body.** A public function's `@doc`: one line on what it does, the `%Subject{}`/permission it requires, and the return-shape tuple — matching the real code. Worked example: `.agent/kb/rules/elixir-doc-contract.md`.
- **Compare an `Ecto.Enum` field on its atoms, never a string literal.** An enum field loads as an atom (`:sent`), so `@run.status in ["sent", "running"]` is *always false* and fails silently — it shipped a costly dead-UI bug (`69d9871`: cancel button + approval banner + output-hiding all dead, nothing flagged it). Worked example: `.agent/kb/rules/elixir-ecto-enum-atom-compare.md`.
- **`nil` is not an empty list — normalize a stored map's value before you enumerate it.** `x["key"] != []` is an equality test, not a list check: a map with no such key compares as non-empty, so the guard passes and the comprehension behind it receives nil (`Protocol.UndefinedError: Enumerable not implemented for Atom`). A schema contract governs WRITES and does not constrain a row already in the column — `Definition.validate_draft_shape/1` requires `"inputs"`, yet rows published under an earlier shape carry no such key, and the run page read the raw `jsonb` and took the whole page down on every render (49 events). Normalize once into a name (`definition["inputs"] || []`) or at the source (`RunbookDraft.from_definition/1`), so the guard and the walk cannot disagree. Sweep: a `:for`/`Enum.*` over a subscript read of a map you did not build, and any `["key"] != []` guard on stored, decoded, or third-party data — a comparison on a value a repo constructor always fills is correct and stays. **Enforced** by `EmisarWeb.TemplateHygieneTest` (Credo cannot see inside a `~H` sigil); the broad AST form was measured 11/11 false-positive and rejected. Worked example: `.agent/kb/rules/elixir-nil-is-not-an-empty-list.md`.
- **A byte budget is derived from byte bounds, and a size failure says "too large".** `validate_length/3` counts GRAPHEMES by default, and a grapheme carries no byte bound — one CJK character is 3 bytes, one family emoji is 25 — so a character limit tells you nothing about wire room. Sweep: free-text `validate_length` maxima with no `count:` reaching a bounded payload (identifier-shaped fields are ASCII by construction); literal `@max_*_bytes` attributes that should be derived; a size comparison sharing an `else` with a validation or resolution failure; and a slice bounding a value against a schema limit counted in different units (JSON Schema `maxLength` counts code points, `String.slice/3` counts graphemes). Worked example: `.agent/kb/rules/elixir-byte-budgets-need-byte-bounds.md`.
- **An acronym is all-caps in a module name.** `EmisarWeb.SCIM.UserController`, `Emisar.SSO.OIDC`, `EmisarWeb.MCP.*` — not `Scim`/`Oidc`/`Mcp`. CamelCase capitalizes each *word*; an initialism is one all-caps unit. (snake_case identifiers stay lowercase — `scim_token`, `oidc_state`, the `/scim/v2` path — the rule is module/alias names only.)
- **Always-present arguments are positional, not buried in `opts`.** `opts` is for the genuinely per-call-optional. A value every caller must supply — a session's `auth_method` — is a required positional argument that forces the caller to decide it, not a `Keyword.get(opts, :auth_method)` that silently defaults to `nil`. Keep in `opts` only what is actually optional (the SSO-only `:user_identity_id`).
- **Don't invent a custom select-result shape; carry the struct.** A read that needs a row's fields returns the **whole struct** — or a tuple of structs (`{user, token}`), preloading what it renders — never a bespoke `select(q, [...], %{a: t.a, b: t.b})` map that every caller and test must learn. A new shape is new surface to maintain; a struct (or `{entity, entity}` tuple) is one callers already know, and it carries new fields for free. Name the function for what it returns (`fetch_user_and_token_by_session_token`, not `fetch_user_…` returning a third element).
- **A test's context is an explicit `%{...}` pattern in the head, never a bare `ctx`/`context`.** `test "…", %{account: account, subject: subject} do` — the entities the test uses read at a glance, and an unused setup key is a warning. Never `test "…", ctx do` then `ctx.account`: it hides the test's real dependencies and silences the unused checks. (See §7.)
- **A test file's `describe` blocks follow the SAME order as the functions in the module under test.** `accounts_test.exs` opens with `fetch_account_by_id/1` because that's the first function in `accounts.ex`; the describes then track the module top-to-bottom, so a reader pairs test↔function by position and spots an untested function by its gap. A new test slots in at its function's position, never appended at the end.
- **Every PUBLIC function in a context has a function-named `describe "fun/arity"` with real tests** — and a concept-named describe (`"MFA lifecycle"`) doesn't count; rename it to the function it exercises. The describe-order rule above exists precisely so a missing function is a visible *gap*; this rule says that gap must be zero. **Enforced** by `Emisar.ContextCoverageTest`, which reads each context's public `def`s and fails the suite if any has no `describe` anywhere in the test tree (add a new context to its `@contexts` list when you create one). Add the describe in module order with §7's happy / denial / cross-account paths — never silence the check.
- **Tests `alias Emisar.Fixtures` and call domain-namespaced fixtures — `Fixtures.Accounts.create_account/1`, `Fixtures.Users.create_user/1`, `Fixtures.Memberships.create_membership/1` — never `import Emisar.Fixtures`.** An `import` dumps every fixture into scope unqualified, so a reader can't tell `account_fixture()` from a local helper and two fixtures can't share a verb; the namespaced call (`Fixtures.<Domain>.<verb>`) reads as what it builds. Fixtures live in per-domain submodules under `Emisar.Fixtures.*`.
- **Shared per-`describe` fixtures go in a `setup` block that returns the context map, not repeated inline in every test.** When a describe's tests all need the same `user` + `account`, build them once — `setup do … %{user: user, account: account} end` — and each test pattern-matches what it uses in its head (`test "…", %{user: user, account: account} do`); only rows a single test needs (and varies) stay inline. Re-calling the same fixtures at the top of every test is the "fixture abuse" smell. (Pairs with the explicit-`%{...}`-head rule above.)
- **Test-writing taste — fixtures for setup state, `Fixtures.<Domain>.<schema>_attrs` factories, explicit entity creation (no `owner_subject()` side-effects), DAMP-over-DRY, no narrative comments, `==`-vs-`=`, `errors_on/1` content asserts + split asserts, bound long attrs, `Repo.one` sandbox checks, changeset-level validation tests — is detailed in [§7 Tests](elixir-layered-contexts.md#7-tests).**
- **Attribution is human-first: who leads, `via` is secondary.** Any surface naming who dispatched a run or caused an audit event leads with the accountable HUMAN by name (the requesting operator, or a credential's owner — email fallback), with the API key / MCP client / channel shown as secondary `via …` context, never replacing the human — multiple keys are all named "Claude Code", but the human behind them isn't. Runs expose domain-owned `{who, via}` through `Emisar.Runs.run_who_via/1`; runbook executions use `Emisar.Runbooks.execution_who_via/1`; both consume explicitly scoped attribution preloads and `Accounts.member_display_name/2`, while approval actor batches go through `Approvals.actor_labels_for_ids/2` → Accounts. The web may word/style those plain facts (`TimeHelpers.accountable_actor_label/1`) but never inspects association load state or credential ownership. Audit resolves the key's owner into the `api_key_owner` refs map (`Emisar.Audit.resolve_references/2`) and renders it via `EmisarWeb.AuditLive.actor_who_via/4` (`actor?` on `AuditLive.ref/1` for the detail card). Sweep: any run/approval/runbook/audit actor label that shows a key/client/source without first resolving the human behind it, or derives a tenant-local name from an unscoped/unloaded association.
- **Product analytics (Mixpanel) goes through ONE seam — `Emisar.Analytics` — server-side only, scoped to MARKETING + GROWTH.** We ship **no** client-side SDK (strict CSP + the "no third-party trackers" brand promise on /trust). **Scope is deliberately narrow:** pageviews + lead capture (funnel), sign-up / sign-in / sign-out (acquisition + retention), and plan (`subscription_changed`). **NEVER send operational telemetry we can read from our own database** — runs, runner connects, approvals, policy edits, pack trust, team changes, runbooks — to a third-party tool (data minimization for a security product). `subscription_changed` is the ONE deliberately-kept domain builder in `Emisar.Analytics.Events`; don't add more, and never an inline `Analytics.track` at a call site or a client `track()`. Pageviews/funnel/identity live in `EmisarWeb.Analytics`: **marketing** pages via the `:browser`-pipeline plug, **console** (LiveView) pages via the `:track_pageviews` `on_mount` hook (`handle_params`, connected-only) since console nav is over the websocket with no controller hit. Console pageviews are `page_viewed` (engagement), NOT a special event — but the operational *domain* events above stay out. Tracking uses **no analytics identifier cookie**: an anonymous visitor is a **weekly**-rotating salted IP+UA hash (`Emisar.Crypto.anonymous_visitor_id/1`, `$device:`-prefixed — the Plausible model), an identified visitor is `user.id` from the auth session; the existing encrypted login/CSRF session may carry bounded first-touch UTM values until sign-in, but never an analytics id. We do **NOT** honor DNT/GPC (first-party analytics isn't a "sale/share", so the headers don't apply — and our audience is GPC-heavy, so honoring it blinded the funnel). Disclose any new processor on `/privacy` + `/trust` + `/dpa` (one list, three templates + the marketing test). A no-op unless `MIXPANEL_TOKEN` is set (off in dev/test). User profiles (`$name`/`$email`) are set at login; account-level **Group Analytics** (group key `account_id`, set on console events + `subscription_changed`) is wired but gated by `MIXPANEL_GROUPS=1` (paid add-on).
- **A user-requested UI fix ships with before/after screenshot proof.** BEFORE editing anything, ensure the work has a claimed task (create even a basic Portal task when none exists), then capture the reported element from the active live-reload server with `./run shot <path> --label before --select '<css>' --group <surface>` (the broken state is unrecoverable once the fix lands, so shoot it FIRST). The command writes into that task's `screenshots/`; use `--task <id>` only to disambiguate multiple active tasks. Fix, let Phoenix reload, re-shoot with `--label after` and the same task/group, LOOK at both crops yourself, then hand the user the before/after paths for review — pixels, not prose. Prefer a stable `data-shot` anchor (`--shot <name>`) when the surface owns one. Workflow + other anchor options: `.agent/kb/rules/design-ui-fix-screenshot-proof.md`.
- **Operator-typed form input survives re-renders and rejected submits — server-side, with no client draft store.** LiveView's patch resets every non-focused input to the server's render, so every typeable field in a `phx-change` form is server-tracked (the change handler assigns the posted params back), and every submit-error branch re-renders the operator's values — never the stale stored ones.Worked example: `.agent/kb/rules/elixir-preserve-operator-form-input.md`.
- **One runbook, one sha-locked draft: publication comes only from that draft, only the live release executes, and the DOMAIN enforces both while the UI merely reflects them.** A runbook is a single row — `definition` + `live_version` are what runs, `draft_definition` is the one unpublished change, and each publish appends a `runbook_releases` row. Never trust the UI's hidden buttons: every mutation judges the LOCKED row inside its own transaction — `Runbooks.save_draft/4` compares the caller's `base_sha` against the row's current editing digest (`{:error, :draft_changed}`), `publish_draft/2` refuses without a draft (`{:error, :no_draft}`) and rechecks readiness against that row's own draft rather than a caller snapshot, `discard_draft/2` refuses when nothing is live (`{:error, :never_published}`), and dispatch refuses a runbook with no release (`{:error, :not_live}`) — the same invariants MCP enforces. The failure this closed: publishing an old draft IN PLACE made it the newest published version, silently flipping what a default Run dispatches to old content. **A state that inverts the whole page's affordances is page identity, not just a notice:** a runbook with nothing live cannot be run from anywhere, so its list row carries `Never published` as a chip on the title line and the run route refuses and redirects — never a quiet banner the operator scrolls past on a tall page. Sweep: lifecycle mutations that accept a caller-supplied row without an optimistic-lock or live check, publish paths taking a definition from the caller instead of the locked row's draft, and page-inverting states (never published, frozen, suspended) whose only marker is a neutral scrollable notice.
- **Multi-runner availability: structural absence blocks; a trust gap narrows.** When one step reaches several runners (a group target), a runner that does not advertise the pack at all makes the action unavailable — declared coverage never silently shrinks — while a runner whose advertised deployment merely holds no trusted version right now (retired, pending, rejected, or drifted) narrows the executable set to the runners that hold trust; zero capable runners is still unavailable, and nothing untrusted is ever selected. One choke point owns the judgment (`Catalog.select_common_action/1`), so the editor picker, dispatch, and model-facing availability cannot disagree. Sweep: any multi-runner availability or dispatch judgment that fails the whole set on a per-runner trust state.
- **A back-link climbs the entity hierarchy one level, never the arrival path and never over a level — and the title bar renders EVERY level, ending in a heading that names THIS page.** Single sign-on → a provider → editing that provider: each `detail_header back=` names and targets the page's direct parent (`back={provider.name}`, not `back="Single sign-on"`), so a page subordinate to ONE record never names the collection. A referrer-shaped back is unstable; a level-skipping one strands the operator mid-review. A page more than one level deep therefore stacks a `<.back_link>` per ancestor BEFORE its `<.detail_header>` — `Runners / <runner> / Run <action>`, `Runbooks / <runbook> / Run` — because `detail_header` renders exactly one crumb and dropping the rest hides the section the operator navigates by. The heading is the page's own job or entity (`Run`, `Execution`, `Draft test`, `Add connection`), never its parent's name: the runbook run page passed the runbook title as both `back` and `title` and shipped `Morning edge readiness / Morning edge readiness`. Sweep: `detail_header back="<collection>"` on pages keyed to a single record's children; routes with two or more segments after a record id whose `<:title>` holds a single crumb; and any `title=`/`back=` pair on one `detail_header` resolving to the same value.
- **A fixed-length cell input owns its cell geometry — the cells never stretch with the container.** One character gets one fixed box (`code_input`: `h-14 w-12`), so six of them are the same control on a 448px auth card and on a 1100px settings panel; `w-full` / `flex-1` / `justify-between` inside the group hands the size to whatever contains it, and that is what shipped six ~200px slabs on the MFA enrollment step while the identical component looked right in the sign-in card. The group left-aligns and may SHRINK below its own width on a tiny phone, never grow, and a caller gets no size override — the component is the only place the box is decided. Same family as §7.54 (a control's geometry belongs to its component): there a caller's FACE resized the BOX, here the container did. Sweep: `code_input` callers, and any `:for`-over-a-length cell group whose child carries `w-full`, `flex-1`, or a `1fr` track. **Pinned** by `EmisarWeb.Components.CodeInputTest`.
- **A row wears ONE button grammar, and a row with MORE THAN ONE verb wears the bordered face.** §2's "navigation is a link" is about a verb that stands ALONE — a section header, a rail, a footer, a row whose only affordance it is — and there it stays the bare brand link with its `cta_arrow`. Two triggers force the bordered `:secondary` face instead: a navigation verb sharing the row with a bordered action button, and **a row carrying two or more verbs even when every one of them only navigates** — the founder read the agents list's `View activity →  Audit trail →` pair as "ugly", because two bare links in an action slot read as a run-on sentence rather than as this row's controls (and §7.47 already counts 1–2 verbs as bordered buttons, 3+ as the `Actions ▾` menu — a two-link row was the gap between those cases). The moment that verb sits in the same action group as a bordered button, §7.47's row grammar wins: `Audit record →` as bare text beside a ringed `Revoke` reads as two unrelated affordances, and the founder called it exactly that ("there should be link and button next to each other, both should be buttons or move link from this place"). Match the peer's `size` and optical height; drop the arrow, which is the *link* affordance. The face belongs to the ROW, not to the per-row permission state — restyling it when the conditional peer button is absent would move the layout between states (§7.55). Sweep: any `<:actions>` slot or `flex items-center gap-*` action cluster holding BOTH a bare `text-brand-400` link and a `<.button>`/`<.confirm_button>`, **or two or more `<.link>` verbs** (the link+button mixes were approvals grants, enrollment keys, runbooks, policies rulesets and SSO provider detail; the two-link shape existed in exactly one place, `agents_live`'s non-manager/revoked branch, and a repo sweep of every action slot confirmed it was the only one). `design-console-ux.md` §7.47.
- **A shared verdict width is a property of a COLUMN of peers, not of the pill.** `risk_pill` therefore ships two structural forms: `variant={:track}` takes the fixed width sized to the longest tier, for pills that stack into one visual column (runner detail's advertised actions, the policy rail's tier breakdown, the pack action list and its trust diff); `variant={:inline}` — the DEFAULT — is content-sized at `<.chip upcase>` metrics, for a pill riding an identity or meta line beside prose. Baking the track width into the component made `HIGH` balloon everywhere it sat inline next to small text. The default is inline precisely because a lone pill has no column to align to; a column is the thing that must opt in. Sweep: `risk_pill` (and any future verdict pill) call sites — classify each as a stacked column or a text line before choosing, and check the widest real data. `design-console-ux.md` §7.41. **Pinned** by `EmisarWeb.Components.RiskPillTest`.
- **One repeated verb wears ONE face per page.** When the same navigation verb appears across parallel headers or rows of a single page and ANY instance is forced into the bordered face by a peer button (the row grammar above), every instance on that page wears the bordered face — a bare brand link above bordered twins below reads as two unrelated affordances, and the founder read the policies page's mixed faces as the targeted rulesets lacking `View activity` entirely. §2's standalone-nav-is-a-link applies to a verb that appears once on the surface. Sweep: one page rendering the same verb string as both a `text-brand-400` link and a `<.button>`; the conditional cross-row mixes (dashboard `setup_step`, team `member_actions`, agents rows) are the open candidates to judge by this rule.
- **One control row, one gap per DIMENSION — the boundary between dimensions is DISTANCE, never a glyph.** A chip/toggle/tab row filtering on more than one dimension gives each its own box and steps the gap up between them (`gap-x-5 gap-y-3` on the outer row). Options inside ONE filter dimension form a segmented control: zero gap, one outer frame, shared dividers, square internal corners, and rounding only at the two outside ends; segmentation changes adjacency only, so it preserves the compact chip density (`px-2 py-1`) rather than inflating into toolbar-sized buttons. A single-option dimension stays one compact rounded toggle. A middot is too quiet to separate dimensions (a vertical rule is shell chrome; the middot's job is joining TEXT metadata, never two controls). Never merge different dimensions into one segmented group. Sweep: flex rows holding 2+ `:for` comprehensions of controls under one gap class, spaced chips that choose one dimension, and bare `·`/`•`/`|` or `w-px` elements between interactive siblings. `design-console-ux.md` §7.58.
- **A gated setting always shows its current value; who may change it rides the lock's tooltip, never a prose tail.** Every account setting goes through `<.gated_setting>`: a member who may change it gets the CONTROL (which already carries the value — a select's selection, a toggle's verb), a member who may not gets that same value as a content-sized locked `<.chip icon="hero-lock-closed-mini">` whose tooltip carries the ONE house line, **"Only owners and admins can change this."**, at every call site (founder's call — a per-setting sentence made the same two roles read as several different rules across one page; it matches the denial flashes' voice, and is knowingly approximate only for the runner cleanup schedule, which also needs unrestricted runner access and keeps the precise wording in its denial FLASH). Never relax a predicate to match the line. The description says what the setting does, the value says where it stands, the lock says who moves it. Sweep: a template branch whose non-permitted arm renders a permission SENTENCE (`Owner/admin only`, `… only — currently …`) where the control was, and any `:if`-gated state tag (`Enforced`, `Required`) beside a title whose sibling control's verb already says it. `design-console-ux.md` §7.59.
- **A read-only VALUE never stretches to fill a control track.** When a column holds a control for some rows and a plain value for others (the Team roster's role dropdown vs the locked/unmanageable role), the fixed track belongs to the CLUSTER and every member stays content-sized inside it — a `<.chip class="w-full">` filling the dropdown's box grows a slab that reads as that dropdown disabled, which is exactly what the founder flagged ("role name looks very ugly"). Right edges align because the cluster is `justify-end` and the track, not the chip, owns the width (§7.55). The same cluster's ACTION slot goes the other way — a verb there wears the bordered face of its peers (`Actions ▾`, `Resend email`) rather than a bare link. Sweep: `w-full` (or `flex-1`) on a `<.chip>`/`<.status_badge>`/`<.identity_tag>` inside a fixed-width track, and value/control pairs sharing one column where the value copies the control's box.
- **A conditional section earns section-separation spacing only when visible content precedes it.** When an empty stream/list makes a discovery, fallback, or permission section the page's first visible result, use the normal content-start rhythm (`mt-6`) rather than preserving the large gap intended to separate two populated sections. Keep the larger separation when rows really precede it. Sweep: conditional sections after possibly empty streamed lists with an unconditional `mt-10`/`mt-12`.
- **Demo seeds model one healthy, believable account, never a test rig.** No pagination/volume filler, no duplicate identities per person, versions from `Emisar.Compat` targets (never pinned literals that rot into "unsupported"), timestamps backdated to where the fact sits in the account's story (lists order by insertion — a seed-time `inserted_at` floats a backdated run to the top and stamps every member "joined 1m ago"), seeded integrations stamped as working, and every seeded mutation leaving the receipts a live path would (a terminal run's audit event). Deliberate teaching states — one offline host with a reason, one pending approval, one mid-swap rotation — survive on purpose; a rose leading a page is a broken account, not a story. Reseeding a shape change needs a FRESH database (seeds converge by inserting what's missing), and the seeder must never re-run against a live stack (it takes over connected runners' leases and the append-only audit keeps the churn). Sweep: seed comprehensions generating N-per-dimension rows, version literals in seeds, and seed-time `inserted_at` on any row a list orders by. Worked example: `.agent/kb/rules/design-demo-seeds-model-a-healthy-account.md`.
- **A wide scrolling table protects its text columns with per-column minimums.** A table-level `min-w` alone lets the browser crush unconstrained prose columns into one-word lines the moment `whitespace-nowrap` columns join the row (the founder's crop: "Effect on sessions and runners" wrapping every word beside the nowrap Credential/Prefix columns). Put `min-w-[14-16rem]` on each long-text `<th>` and let the wrapper's `overflow-x-auto` absorb the total; the table-level floor stays as a harmless minimum. Sweep: `min-w-[NNNpx]` tables whose header row mixes nowrap and unconstrained prose columns.
- **An inline-flex chip dropped into running prose carries `align-middle`.** An inline-flex's baseline is not the text line's baseline, so a `status_badge` or icon-`chip` inside a sentence rides visibly off the line (the founder flagged `● error` floating beside its sentence on the troubleshooting page). The COMPONENT owns the correction — `align-middle` on `status_badge`'s root and `chip`'s icon branch — never a per-call-site nudge; `vertical-align` is inert inside flex/grid cells, so console surfaces are untouched. Sweep: any shared `inline-flex` badge/chip rendered mid-paragraph in docs or marketing templates whose component lacks `align-middle`. `design-console-ux.md` §7.17 family.
- **A metadata stack keeps one vertical row gap.** Give adjacent status, activity, and scope rows the same explicit spacing; a conditional row owns its margin so hiding it removes the gap too. Keep stronger separation from the identity heading outside the stack. Sweep: card metadata blocks where one child has `mt-*` while an adjacent conditional child relies only on line-height. `design-console-ux.md` §7.82.
