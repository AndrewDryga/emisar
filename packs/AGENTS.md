# packs — how we build (the action-pack catalog)

`packs/` is the catalog of **infrastructure actions** the runner executes and the portal exposes to operators and LLMs (via MCP). Each `packs/<name>/` is a `pack.yaml` manifest plus `actions/*.yaml` — 100 packs / 1,682 actions today. **This is attack surface**: every action declares exactly what may run on a host, so the runner and policy can enforce a hard boundary. Read the root `../AGENTS.md` (the creed) first. The authoritative schema is the Go types in `runner/pkg/actionspec` + `runner/pkg/packspec`; this file is the conventions.

## The gate (verify before claiming done)

Both are required before committing a pack change:

```
./run gate packs
./run test packs [name-pattern]
```

A pack that declares `setup.host_access` also requires:

```
./run test pack-access [pack-name]
```

That suite executes the exact published grant and verification commands on a
disposable systemd host, proves the mapped protected-resource operation is
denied before the grant, then proves it still works under `no_new_privs` after
the Emisar service and any declared recreated resource restart. The ordinary
pack behavior plan remains the provider/action proof; a host-access fixture
never substitutes a stub for vendor behavior.

`./run gate packs` validates every pack with the runner's load-time checks,
verifies the cross-language hash goldens, rebuilds the catalog into a temporary
directory and byte-compares it with the committed artifact, then runs the
focused Portal catalog tests — but it never executes a pack action, so the
behavior cases are required too; the gate alone has shipped regressions. Use
`./run pack check <name>` while editing one pack. A malformed pack breaks
**both** consumers: the runner (loads + SHA-256-pins each pack at runtime) and
the portal (which serves the catalog **artifact** built from `packs/`).

**Validate is not the whole gate — a pack add/change also touches these, every time:**

1. **`packs/README.md`** — keep the one catalog summary current, but do not duplicate the generated pack inventory in prose. The live registry and bundled `catalog.json` own per-pack counts, risk, and setup; a hand-maintained README table drifts and makes the install/authoring path harder to find. Verify the summary totals against reality from `packs/`: `find . -mindepth 1 -maxdepth 1 -type d -exec test -f '{}/pack.yaml' ';' -print | wc -l` and `rg -g 'pack.yaml' '^  - actions/' . | wc -l`.
2. **Regenerate the bundled catalog artifact in the SAME commit** (since `4fe4349d` the portal no longer scans `packs/` — it uses `portal/apps/emisar/priv/packs/catalog.json` to seed a fresh VM, while `Emisar.Catalog.PackBaseline` reads auto-trust from the installed snapshot that the configured published catalog refreshes, so a stale artifact means a fresh VM auto-pins the old set until its first successful refresh): fetch `https://registry.emisar.dev/v1/catalog.json`, then run `packctl catalog build --packs ./packs --out ./dist/packs --previous <downloaded-live-catalog>` (**the live catalog is authoritative; using the committed artifact can carry an unpublished intermediate version forward after a canceled release; always pass `--previous` or every pack's version-window history rebuilds EMPTY and the monotonic guard on each pack's `retired_below` floor is skipped**), copy the built `catalog.json` over `portal/apps/emisar/priv/packs/catalog.json`, then run `mix test test/emisar/catalog/pack_baseline_test.exs test/emisar/catalog/published_registry/cache_test.exs` from `apps/emisar`. Use the committed catalog only when there is no live history to download — bootstrapping an empty registry, or repairing a missing/unparseable live pointer (CD's `packs-publish` does that fallback automatically; restore a bucket generation instead when the exact prior history matters — `packs/PUBLISHING.md` → Rollback). `catalog build|publish` is the maintainer tool `packctl`, not the host `emisar` binary — build it from `runner/` (`go build -o ../bin/packctl ./cmd/packctl`); `bin/emisar` is still what runs `pack validate`, while `./run pack hashes` owns the cross-language golden check.
3. **Portal pickup needs a catalog sync, not wiring.** There is no list to edit anywhere in `portal/` — the installed catalog snapshot, boot-seeded from the bundled artifact and refreshed from the configured registry, drives the marketing `/packs` + `/packs/:id` pages, the sitemap, and the registry API. Run `./run pack sync <name> --fix`; the active `./run serve` process recompiles the changed artifact. Confirm against the URL from `./run urls` with `/packs.json` and `/packs/<name>`. A packaged release image still needs a rebuild; prod re-bakes on the next deploy.
4. **redis/cassandra byte changes** — refresh the cross-impl hash golden (below).
5. **Contract changes bump `version`** (trust model, below); brand-new packs start at `0.1.0` and need no bump until first committed. **A version here is dot-numeric only** — `0.3.15`, never `1.0.0-rc1` or `2.0.0+build`. Four things judge a version and three differ on purpose: the loader is permissive because a third-party pack may label itself anything, the portal's runner_action column matches it because it stores what a runner advertised, the MCP projection accepts SemVer suffixes, and `packctl catalog build` requires strict dot-numeric so the retirement compare can parse each component as an integer. A suffixed version therefore validates, installs, advertises, produces a valid `pack_ref` and can be signed — and can never be published. `./run check packs` now refuses it at authoring instead of at release (`validatePackVersions`); the same rule covers `retired_below`, which the same parser compares.

**Publishing to the public registry (GCS).** `packctl catalog build --packs ./packs --out ./dist/packs` produces the immutable, versioned artifacts — `catalog.json` + a content-addressed snapshot, `suggest.json`, the JSON schemas, and one content-addressed `pack.tar.gz` per pack — all hashed with the same loader `emisar pack validate` uses, so the published `content_hash` matches byte-for-byte. `packctl catalog publish` appends them to the `emisar-pack-registry` bucket (immutable objects never overwritten; the latest catalog pointer regresses only via bucket versioning). Publishing **appends** — a byte change for an already-published `id/version` fails the build until you bump `version`. Full runbook (build/publish/verify/rollback): **`packs/PUBLISHING.md`**.

**Editing `redis/` or `cassandra/`? Refresh the cross-impl hash golden too.** The portal test `apps/emisar/test/emisar/catalog/published_registry_test.exs` pins the `content_hash` of **redis** (exec-only) and **cassandra** (has a script-kind action) byte-for-byte — the proof that the Elixir `Emisar.Catalog.PublishedRegistry` and the Go runner hash a pack identically. **`emisar pack validate` does NOT run that test**, so ANY byte change to those two packs (including a catalog-wide sweep that touches their action text) leaves the golden stale and the *portal* build RED — silently, from the packs side. This drift is caught mechanically by the Go implementation behind `./run pack hashes`; the staged commit check calls it whenever redis or cassandra bytes change and fails open only when `bin/emisar` is unavailable. Refresh both literals with `./run pack hashes --write`; `./run gate packs` confirms the Elixir hash agrees. Commit the golden refresh **with** the pack change.

## Anatomy

```
packs/<name>/
  pack.yaml        # id, name, version, description, requires/detect/setup, actions: [actions/*.yaml]
  actions/*.yaml   # one action each (kind: script also ships scripts/*.sh)
  test/
    cases.yaml      # semantic behavior cases
    compose.yaml    # this pack's isolated disposable SUT
    fixtures/       # optional pack-owned service config or seeded state
```

The first service in a behavior plan is its primary SUT. Its Compose image or
pack-local Dockerfile consumes `PACKTEST_VERSION` and `PACKTEST_DIGEST`.
`cases.yaml` declares unique supported version rows with exact digests and
marks exactly one default matching Compose. Relevant changes run every row for
that pack; the weekly workflow runs the complete compatibility matrix. Keep
helper and fixture image versions independent when they are not the product
under test. Every case runs in its own disposable Compose project, defaults to
a non-root runner identity, and owns its setup and terminal SUT lifecycle.
Credentials use unique declared canaries. See the
[risky-action behavior rule](../.agent/kb/rules/packs-risky-actions-require-behavior-or-reason.md)
for the evidence, exception, identity, and secret-testing contract.

An **action** declares: `id` (`<namespace>.<name>`), `risk` (low|medium|high|critical), `kind` (exec|script), `args` (typed + validated), `execution` (binary + argv template, timeout, env), and `output` (parser + byte caps + redaction).

## Conventions (non-negotiable — this is a security product)

- **The cloud/LLM never controls the shell command.** `execution.command.argv` is a list and `{{ args.x }}` substitutes into its slots. Prefer a real binary's argv. When an action genuinely needs shell features (pipes, `${VAR:-default}`), `binary: /bin/sh` + a fixed `-c '<pipeline>'` program is supported — the program is *authored here, never cloud-supplied*. Open-ended strings, paths, arrays, and one-sided numeric args MUST reach it through `execution.env` or a whole positional argv element after the program; only finite `enum`/`allowed` choices and two-sided bounded numbers may render into program text. The loader enforces this at authoring time. A regex constrains shape; it is not a shell-isolation boundary. The **`shell` pack is the separate break-glass**: there the OPERATOR supplies the whole command (arbitrary `/bin/sh -c`, `risk: critical`, default-denied — staging only).
- **Binary paths are bare, PATH-resolved names** (`systemctl`, `psql`), never absolute. `/bin/sh` is the sole absolute exception — used by the `shell` break-glass pack AND by the many read actions that need a shell pipeline.
- **A script action that needs `bash` DECLARES `bash` in `requires.binaries`.** `/bin/sh` is on every host we support and needs no declaration; `bash` is not — a Debian slim image, an Alpine host, or a hardened build may carry only busybox `ash`. Undeclared, the pack installs cleanly, the action shows up in the catalog, and it fails at dispatch, after an operator approved it. Eight packs and 75 actions sat in this gap because the loader validates `execution.command.binary` and never looks at `execution.script.interpreter`. **Enforced** by `./run check packs` (`validatePackInterpreterBinaries`, fixture-verified to fire and to leave `/bin/sh` alone).
- **Bound every LLM-supplied arg.** Strings/paths get `max_length`; prefer `enum`/`allowed`/`pattern` whitelists over blocklists; path args use `allowed_paths`/`denied_paths` (symlink-contained). An unbounded string arg is a DoS hole. **An anchored `pattern` is NOT path containment.** `^/var/log/nginx/[A-Za-z0-9._/-]{1,128}$` looks tight but `.` and `/` are literal charset members, so it still matches `/var/log/nginx/../../../etc/shadow` — the pattern constrains lexical shape, nothing more. A path arg that a command actually *reads/writes* MUST also declare `allowed_prefixes` (subpaths) or `denied_paths`/`allowed_paths`, which is the only thing that activates the runner's `Clean`+`EvalSymlinks` containment (`internal/validation/args.go` `applyPathValidation`) that collapses `..` and blocks symlink escape. Without it a `low`, no-approval read escapes its directory to any root-readable secret (`/etc/shadow`, `.pgpass`, arbitrary `.env`) — redaction is pattern-bound and won't catch most of them. Sweep signal: any `pattern: "^/…"` on a path arg with no sibling `allowed_prefixes`/`denied_paths`/`allowed_paths` in the same `validation:` block. Use `allowed_prefixes` (not `allowed_paths`, which is exact-match and rejects real files under the dir).
- **Packs are generic across every fleet — never hardcode an environment-specific allowlist.** An arg that names a *deployment-specific* identifier — a systemd unit, a service, a database, a host — must NOT be a hardcoded `enum`/`allowed` list (`{cassandra,nginx,postgresql,docker}`): that list is wrong for the next fleet and can't touch `nomad`/`consul`/`frr`/whatever this operator actually runs. Bound its syntax and size with an anchored `pattern`, then lean on **operator policy/admission** to gate WHICH targets may be acted on — that's the layer that knows a given fleet's units. Reserve `enum`/`allowed` for genuinely environment-INDEPENDENT value sets (a log level, `stream: stdout|stderr`, an output format, an enum of API sections). (The over-narrow `systemctl_restart` unit enum was removed for exactly this reason — b7664f3f.)
- **Risk is honest.** A tier describes the action; the account's policy maps tiers to gates, and the shipped default auto-runs `low` **and** `medium`, requires approval for `high`, and denies `critical` — so under that default a tier is a promise about what may happen without a human in the loop. `low` = pure reads with no secret-bearing output; `medium` = bounded, recoverable state changes (or reads with the blast-radius caveats below); `high` = destructive mutations AND any read that dumps arbitrary secret-bearing state (a full config dump, an environment/property dump, message bodies, crontab command lines) — redaction is pattern-bound and cannot make such a dump safe; `critical` = unrestricted (default-deny). Mislabeling an action one tier lower bypasses the approval gate. **`low` also means no *inbound* exposure and no heavy blast radius — not just no host mutation.** An action that opens a listener, binds a port, or starts a server is **at least `medium`** even when it's transient and touches no files (opening the host to inbound connections *is* the state change); so is a probe that generates **sustained, link-saturating traffic** — real congestion on a shared path — as opposed to a cheap `ping`/`curl`. Reserve `low` for pure reads and cheap, bounded probes. (Sweep signal: any action that starts a server / `--listen` / binds a port, or floods a link. iperf3's `server` (inbound port) and `client`/`udp` (link-saturating) are `medium` for exactly these reasons, and the pack ships uniformly `medium`.)
- **Risky behavior is accounted for, not percentage-covered.** In a modeled pack, every new or changed `high`/`critical` action has a successful semantic case or a known machine-readable exception. A failure-only case does not prove the action works. Graduate packs to complete accounting rather than chasing a global coverage percentage.
- **Redact at the source.** `output.redact[]` (regex/literal) scrubs stdout/stderr before it leaves the host; mark secret args `sensitive: true`. An uncompilable redaction rule fails validation (fail-closed).
- **Design actions not to emit secrets — redaction is defense-in-depth, not a license to print.** `output.redact[]` (the runner's streaming `internal/redact`) is the fail-closed LAST line, but it is **pattern-bound**: a secret whose shape no rule matches leaks (the streaming-redaction secret-leak fix is exactly why). So don't emit them in the first place — no `printenv` / whole-environment dumps, no private-key blocks, no credential-bearing connection strings, no `cat` of an unfiltered config/secrets file. Pass a secret to a command via `execution.env` (mark the arg `sensitive: true`), never argv, and never echo it to stdout. An action whose JOB is to surface env/config (a debugging read) is the rare exception: scope it tightly, label its risk honestly, and say so in the description — never let "the redaction pass will mask it" stand in for the design.
- **No env hijack vectors** in `execution.env` — `LD_*` / `DYLD_*` / `BASH_ENV` are rejected.
- **Greenfield:** edit the pack in place; **bump `version` when its contract changes** — the runner re-pins the hash, and the new hash needs its own trust decision: auto-pinned once the configured catalog publishes it, an operator review until then (below).
- **Retire ONLY on a security or critical fix — never a routine bump.** `retired_below` fails a pinned runner CLOSED at dispatch (`pack_retired`) and forces the whole fleet off the version, so it is reserved for versions genuinely UNSAFE to keep running: a closed security hole (an under-bounded arg, a secret-emitting read, a path-escape, a mislabeled risk that skipped approval) or a critical correctness fix (an action that could corrupt state, take down a host, or act on the wrong target). For those, a `version` bump alone isn't enough — a runner still advertising the vulnerable version keeps executing it until an operator happens to update — so in the SAME commit as the fix, raise the pack's retirement floor: set `retired_below:` in `pack.yaml` to the new (fixed) `version` (dot-numeric), retiring every version below it, and a pinned runner then fails closed with `pack_retired` instead of running the hole. The floor is monotonic in the normal publication path — `packctl catalog build --previous` refuses to lower or drop an already-published one; author it in git, review it in the PR. The portal runtime does NOT re-enforce that: a structurally valid catalog that lowers or drops a watermark is logged as a regression and still served, so monotonicity is the publisher's guarantee, not a runtime invariant. Full runbook in `packs/PUBLISHING.md` → *Retiring older versions*. **A routine bump does NOT retire** — a new action, a description tweak, a non-security behavior change bumps `version` and leaves `retired_below` untouched; the older version stays trusted and usable and operators update at their own pace (only a retired version is ever blocked — an outdated-but-safe one keeps working, and the portal nudges the update non-blockingly). Over-retiring fails safe versions closed fleet-wide and floods operators with pending/retired reviews for changes that never warranted it. Sweep signal (both directions): a security/critical fix that leaves `retired_below` untouched (under-retire), OR a `retired_below` raised in a commit that isn't a security/critical fix (over-retire).
- **A required credential says WHERE it comes from, not just what it needs.** A `setup.env` var the pack cannot run without is useless to an operator who does not know how to obtain one, and `setup` is now rendered on the public `/packs/<id>` page — read BEFORE installing — as well as by `emisar pack info` on the host, so this is the page that has to answer it. Name the console location or the exact command that mints the credential (`Settings → Auth Tokens`; `mc admin user add <alias> <access> <secret>`; `GRANT pg_monitor TO emisar`) alongside the permission or scope it needs. Keep it to the durable part — the object to create and the privilege to give it — rather than a deep menu path that rots with the vendor's next redesign, and do not restate what the summary already says. A required var that is a filesystem path or an address (`GIT_REPO`, `KAFKA_BOOTSTRAP`, `HAPROXY_SOCK`) is not a credential and needs no such note. **Setup prose is lightly formatted, and the `/packs/<id>` page renders it:** wrap identifiers in markdown backticks — env var names, config keys like `execution.inherit_env`, paths, and commands — and link with `[label](https://…)` when the vendor has a stable page that mints the credential, ideally one that pre-selects the scope (`https://github.com/settings/tokens/new?scopes=repo`). Only `https://` links render; anything else stays literal, a bare URL is never auto-linked (several packs put example connection strings in their prose), and a link label carries no backticks of its own.
- **Host authority maps to exact actions and a persistent recipe.** If an action needs a protected file, socket, service identity, group, ACL, capability, polkit rule, or root, declare it in `setup.host_access` instead of burying it in `setup.notes`. Name every affected action, give copyable commands that survive the target daemon and runner restarting, prove the resulting access, and state the authority the grant gives the runner identity. Emisar renders these commands but never runs them. See [`../.agent/kb/rules/packs-host-access-recipes-map-exact-actions.md`](../.agent/kb/rules/packs-host-access-recipes-map-exact-actions.md).
- **Pack suggestions use only explicit detection evidence.** `requires.binaries` says what an installed pack needs to execute; it never becomes a `detect` fallback. Author deliberate service-specific `detect` signals or leave the pack out of host suggestions. See [`../.agent/kb/rules/packs-suggestions-use-explicit-evidence.md`](../.agent/kb/rules/packs-suggestions-use-explicit-evidence.md).
- **A read/enumerate action's description leads with a searchable verb.** The MCP catalog is what an LLM keyword-matches against, so open a read action's `description` with the verb of the job — **List** (a collection), **Show**/**Get** (state or one thing), **Tail**, **Dump**, **Count**, **Check** — never a bare noun ("All jobs…", "Active sessions…", "Server peers…"), which an LLM searching *"list nomad jobs"* will miss. Every description — read or mutating — opens in the **imperative** (`List…`, `Restart…`, `Delete…`), never third-person indicative (`Lists…`, `Restarts…`), and coordinate verbs in that opening sentence stay imperative too (`Force a stats dump and read it`); a descriptive clause about a named subject keeps its own voice (`a scan that repairs objects`, `— triggers a rolling update`). A CLI-command opener counts when its verb is searchable (`` `kubectl get pods` ``, `` `systemctl list-units` ``, `` `ip neigh show` ``) — keep the command for operators; the leading verb is for discovery. This is description copy only: leading with a verb never changes `risk`, args, or execution, but it **is** a contract change to the catalog text, so it still bumps `version`.

## Trust model

The runner SHA-256-hashes each pack on load and advertises it; the portal verifies every dispatch against the exact `(pack id, version, hash)` the account currently trusts. An advertised triple that matches the **configured published catalog** — its current entry or a retained history entry — auto-pins as trusted. Anything else stays **pending** until an operator Trusts or Rejects it on the Packs page: a hash the catalog doesn't carry, a hand-edited tree, or a pack distributed by a registry this deployment hasn't configured as its catalog. A changed pack → hash mismatch → `pack_untrusted` until re-trusted. A pack edit is an operator-visible event, never a silent change — which is why honest `version` bumps and risk labels matter.

The hash is the binding, not the authority: SHA-256 ties an expected value to exact bytes, it does not authenticate who published them. The trust decision comes from the configured catalog or from an operator. A compromised catalog publisher can therefore authorize bytes already installed on a host, choose the risk and kind that policy evaluates for those bytes, and set, lower, drop, or raise retirement floors. It still cannot install bytes, bypass the runner's descriptor and argument checks or local admission, or erase audit.
