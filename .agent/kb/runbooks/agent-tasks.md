# Agent tasks and batch execution

Read this when creating, claiming, completing, recovering, or batch-processing
tasks. The [root manual](../../../AGENTS.md) owns scope and authorization.

## Working state

Each project uses `.agent/tasks/<state>/<id>/task.md`, with `state.md` as the
overwritten resume snapshot and `log.md` as the append-only reasoning journal.
Read state, log, then the specification before resuming the current task.
The directory is the status: `00_todo`, `10_in_progress`, `50_blocked`, `99_done`.
Task state, backlog, decisions, and screenshots are local and gitignored.

The host CLI owns transitions. In a Coop box without `coop`, make the corresponding
folder move. A status checkbox is not a substitute for a transition.

## Implement one task

1. Use `coop tasks ls` to find the task matching the request. Create one with
   `coop tasks add --project root "<title>"` or the owning project when needed.
   Fill task.md with context, acceptance, and approach. Claim it with
   `coop tasks claim <id>`; skip another agent's active claim.
2. Implement the requested behavior, preserving unrelated WIP. Run focused checks
   while working and the touched project's canonical final gate before committing.
3. Stage only task-owned files/hunks. Make one focused commit ending with
   `Coop-Task: <id>`. `git log` is the changelog; do not create a changelog file.
4. Append what changed and why to log.md. Overwrite state.md with the completed
   outcome and validation. Cite the task id in notes, not a commit SHA: Coop may
   re-sign box commits, changing their SHAs.
5. Use `coop tasks done <id>` only when the gates are green, the commit exists,
   and the notes are complete. Source completion does not imply deployment.

Keep screenshots in the claimed task's `screenshots/`, grouped with `--group`.
`./run shot` and `./run capture console` select the sole active task; use `--task`
when several are active. Inspect captures before citing them. Committed docs images
generated by `./run capture docs` are the exception.

## Findings and decisions

Small safe cleanup directly supporting the task can share its commit. Record a
ready but separate fix with `coop tasks add`; a large/unscoped idea belongs in
`coop backlog add`. The `xx_backlog` drawer is outside the lifecycle and never
auto-worked. Product ideas requiring founder review remain there until promoted.

Missing evidence is work: verify the API, reproduce the failure, inspect an isolated
SUT or use authorized live reads. A blocked task requires a human decision or new
authority. Use `coop tasks block <id>` and fill its decision.md with the decision,
options, recommendation, and completed independent work. `coop tasks decisions`
lists them; `coop tasks unblock <id>` returns an answered task to todo.

## Explicit batches and recovery

Only an explicitly requested batch or `coop loop` processes successive queue items.
Claim the first actionable todo in the authorized queue/scope, complete its lifecycle,
then continue. Do not stop while an actionable task remains in that batch. Skip live
claims and blocked decisions. An interactive question does not start a queue sweep.

Before a handoff, record the exact next action, accepted constraints, completed
checks, evidence, and pending processes. On the host `coop tasks release` hands back
a claim while leaving it in_progress for loop adoption; it does not move it to todo.
Establish that a claim is orphaned before recovering it through Coop. Reconcile the
batch's done tasks with their Coop-Task trailers after an interrupted commit/transition.
Never adopt another active agent's work or delete done tasks automatically; archive
pruning is a separate human operation.

In a box, await or terminate owned jobs before ending the turn. Backgrounding a
gate or consult does not keep the box alive. Keep async work within the active
session and record any verification that could not finish.
